第 30 课 · LRU 缓存

LRU 缓存 = 哈希表 + 双向链表。哈希表负责“按 key 一步找到节点”，双向链表负责“按最近使用的先后排好队，能一步把任意节点挪到队首、一步删掉队尾”。两者合起来，get 和 put 都是 O(1)。

开始前要会：Python —— 魔法方法（__getitem__ / __setitem__ / __len__ / __contains__）、异常（raise KeyError、try/except）、字典的 get、类型标注（X | None、引号前向引用）、functools.lru_cache、lambda、f-string 的 !r；前面的课 —— 第 4 课 · 哈希表、第 29 课 · 链表高频技巧（哑节点）。实战部分用的 OrderedDict（move_to_end / popitem）在本课「实战里怎么写」里就地讲。

实战里怎么写：先别急着手写

缓存在真实项目里到处都是：查汇率、查用户资料、读配置、渲染模板。内存有限，满了就得扔掉一些，“扔掉最久没用的”就是 LRU。业务代码里几乎没人手写链表，Python 标准库已经有两样现成的：

场景用什么代价
给函数的结果做缓存（参数相同，结果就相同）functools.lru_cache(maxsize=N) 装饰器读写 O(1)；只能整个清空，不能单独删掉一项
自己控制读写：按 ID 缓存、手动让某一项失效collections.OrderedDict + move_to_end / popitem(last=False)读写 O(1)；淘汰逻辑要自己写几行
多个进程或多台机器共用一个缓存Redis 之类的缓存服务（配置成 LRU 淘汰）每次读写多一次网络往返
from collections import OrderedDict
from functools import lru_cache

@lru_cache(maxsize=256)
def exchange_rate(currency: str) -> float:
    return fetch_rate_from_bank(currency)      # 很慢；同样的参数第二次直接从缓存拿

exchange_rate.cache_info()                     # CacheInfo(hits=..., misses=..., maxsize=256, currsize=...)

class SessionStore:
    """最多保存 capacity 个登录会话，满了踢掉最久没活动的那个。"""
    def __init__(self, capacity: int) -> None:
        self.capacity = capacity
        self._sessions = OrderedDict()         # 会话 ID -> 用户名，越靠后越新

    def login(self, session_id: str, user_name: str) -> None:
        self._sessions[session_id] = user_name
        self._sessions.move_to_end(session_id)  # 挪到最新
        if len(self._sessions) > self.capacity:
            self._sessions.popitem(last=False)  # 弹出最旧的

    def user_of(self, session_id: str) -> str | None:
        if session_id not in self._sessions:
            return None
        self._sessions.move_to_end(session_id)  # 查到也算一次活动
        return self._sessions[session_id]

题意（LeetCode 146）

设计一个容量为 capacity 的缓存，支持两个操作：

  • get(key)：key 在缓存里就返回它的值，否则返回 −1。
  • put(key, value)：写入或更新。如果写入新 key 时缓存已经满了，先把最久没有被用过的那一项淘汰掉。

“用过”包括 get 读到它，也包括 put 写它（新写入或者更新）。两个操作都要求 O(1)。

练习里的 LRUCache 做成和 dict 一样的用法：put(key, value) 写成 cache[key] = value，get(key) 写成 cache.get(key, -1)；cache[key] 找不到时和 dict 一样抛 KeyError。下面讲解和动画仍沿用题目里的 get / put 两个名字。

例子（capacity = 2，左边是最近用过的，右边是最久没用的）：

操作返回操作后缓存（新 → 旧）说明
put(1, 1)1
put(2, 2)2, 1
get(1)11, 21 被用了，挪到最前
put(3, 3)3, 1满了，淘汰最久没用的 2
get(2)−13, 12 已经被淘汰
put(4, 4)4, 3满了，淘汰最久没用的 1
get(1)−14, 3
get(3)33, 4
get(4)44, 3

生活里的类比：书桌上摞着一叠书。每次用完一本，就把它放回最上面；书桌放不下了，就把最底下那本（最久没碰过的）拿走。LRU 缓存就是这叠书。

暴力做法为什么慢

  • 只用一个 Python 列表按顺序存：get 时要从头找 key，O(n)；找到后挪到最前面，要把前面的元素都往后挪，又是 O(n)。
  • 用字典存值，再给每个 key 记一个“最后使用时间”：get 是 O(1) 了，但淘汰时要扫一遍所有 key 找时间最早的，O(n)。

问题在于我们同时需要两种能力：按 key 快速找到，以及维护先后顺序，并且能快速调整。没有哪一种单独的结构能同时做到。

关键观察：两种结构各管一件事

  • 按 key 找：哈希表（第 4 课），O(1)。
  • 维护顺序：需要支持三件事，都要 O(1)：把中间某个节点摘出来、把节点插到最前面、删掉最后面的节点。数组做不到（中间删除要挪元素），链表可以：只要手里已经拿着那个节点，改几个指针就行。

把它们连起来：哈希表的值不存 value，而是存链表节点的引用，value 放在节点里。这样 get 时先通过哈希表一步拿到节点，再在链表里一步把它挪到最前面。

key_to_node：1 ↦ 节点①3 ↦ 节点③
head 哨兵⇄1:1⇄3:3⇄tail 哨兵（越靠左越新）

为什么必须是双向链表

要把节点 x 从链表中间摘掉，得让 x 前面那个节点的 next 跳过 x。单链表只能往后走，不知道 x 前面是谁，只能从头找，O(n)。双向链表的每个节点多存一个 previous，前一个节点直接就能拿到，摘除就变成 O(1)。

为什么节点里还要存 key

淘汰时，我们是从链表尾部拿到“最久没用”的那个节点的。删掉它之后，还要把它从哈希表里删掉，而删哈希表需要 key。所以节点里除了 value，还要存一份 key。

为什么用两个哨兵节点

在链表两端各放一个不存数据的节点 head_sentinel 和 tail_sentinel，真实节点都夹在它们中间。这样任何真实节点的前面和后面一定有节点，摘除和插入时不需要判断“是不是第一个”“是不是最后一个”“链表是不是空的”。这和第 29 课的哑节点是同一个想法，只是两头都放。

  • 最近用过的节点：head_sentinel.next。
  • 最久没用的节点：tail_sentinel.previous。
  • 链表为空：head_sentinel.next is tail_sentinel。

两个基本动作

get 和 put 都是由这两个动作拼出来的。它们只改链表，不动哈希表。

def _remove_node(self, node):
    # 让 node 的前后两个节点直接相连，node 就被跳过了
    node.previous.next = node.next
    node.next.previous = node.previous

def _add_to_front(self, node):
    # 插到 head_sentinel 和原来的第一个节点之间
    first_node = self.head_sentinel.next
    node.previous = self.head_sentinel
    node.next = first_node
    self.head_sentinel.next = node
    first_node.previous = node

插入要改四个指针：新节点自己的两个，加上左右邻居各一个。先用 first_node 记住原来的第一个节点，因为改完 head_sentinel.next 以后就拿不到它了（第 29 课反复强调的“改指针前先记住”）。

get 和 put（也就是 cache[key] 和 cache[key] = value）

def __getitem__(self, key):            # cache[key]，对应题目的 get
    node = self.key_to_node.get(key)
    if node is None:
        raise KeyError(key)            # 不在缓存里：和 dict 一样抛 KeyError
    self._remove_node(node)            # 用过了：从原来的位置摘下来
    self._add_to_front(node)           # 放到最前面
    return node.value

def get(self, key, default=None):      # cache.get(key, -1) 就是题目要的 get
    try:
        return self[key]
    except KeyError:
        return default

def __setitem__(self, key, value):     # cache[key] = value，对应题目的 put
    node = self.key_to_node.get(key)
    if node is not None:               # 已经有这个 key：更新值，也算用过
        node.value = value
        self._remove_node(node)
        self._add_to_front(node)
        return
    if len(self.key_to_node) == self.capacity:      # 满了：先淘汰最久没用的
        least_recent_node = self.tail_sentinel.previous
        self._remove_node(least_recent_node)
        del self.key_to_node[least_recent_node.key]  # 节点里存了 key，才能删哈希表
    node = DoublyLinkedNode(key, value)
    self._add_to_front(node)
    self.key_to_node[key] = node

为什么是对的

整个结构始终保持两条规则（叫做“不变式”）：

  1. 哈希表和链表里装的是同一批 key：新增时两边都加，淘汰时两边都删，更新时两边都不增不减。
  2. 链表从前到后，是按“最后一次被用到的时间”从新到旧排的：每次 get 或 put 用到一个节点，都把它挪到最前面，它就是最新的；其余节点的相对顺序不变。

有了第 2 条，tail_sentinel.previous 一定是最久没被用过的节点，淘汰它就是 LRU 要求的行为。有了第 1 条，len(self.key_to_node) 就是缓存里的项数，可以用来判断满没满。

复杂度

操作用到的步骤时间
get查哈希表 + 摘节点 + 插到最前O(1)
put（更新）查哈希表 + 改值 + 摘节点 + 插到最前O(1)
put（新增，需要淘汰）查哈希表 + 摘掉尾部节点 + 删哈希表 + 新建节点 + 插到最前 + 写哈希表O(1)

空间是 O(capacity)：每一项占一个链表节点和一个哈希表条目。

怎么认出这类题

  • 题目让你“设计一个数据结构 / 类”，并要求某几个操作都是 O(1)：通常就是把两种结构拼起来，哈希表负责按 key 定位，另一种结构负责顺序或随机访问。
  • 出现“最近最少使用”“最久未使用”“淘汰”“缓存”“容量满了”这些词：LRU 本题或它的变体。
  • 出现“使用次数最少的先淘汰”：LFU，要在 LRU 的基础上再按使用次数分组。
  • 要求“在 O(1) 时间里删掉中间的某个元素”：哈希表找到它 + 双向链表删除它。

动手玩

先点 播放 LeetCode 示例，用“上一步 / 下一步”慢慢看：橙色是这一步正在处理的节点，绿色是刚放到最前面的节点，红色字的是被摘下来、或被淘汰的节点。留意每次 get 命中时节点怎么从中间被摘下、再插到 head 哨兵后面；每次满了以后淘汰的为什么总是 tail 哨兵前面的那个。然后自己改 key 和 value，点 get / put 试试，比如对已有的 key 做 put，看它是否也会挪到最前面。

最容易错的地方

  • 淘汰时只删了链表节点，忘了删哈希表（或者反过来）。之后 get 这个 key 会拿到一个已经不在链表里的节点。
  • 节点里没存 key，淘汰时不知道该删哈希表里的哪一项。
  • get 命中后忘了挪到最前面：get 也算“用过”。
  • put 已存在的 key 时又新建了一个节点：应该更新原节点的值并挪到最前面，否则链表里会有两个同 key 的节点。
  • 插入时改指针的顺序不对：先改了 head_sentinel.next，原来的第一个节点就找不到了。先用 first_node 记住它。
  • 先淘汰还是先插入：容量满时先淘汰再插入。如果先插入再淘汰，要注意别把刚插入的节点淘汰掉（capacity = 1 时最容易出错）。

自测

1. 为什么不用单链表？ get 命中后要把节点从链表中间摘下来，这需要知道它前面的节点。单链表只能从头找前一个节点，是 O(n)；双向链表每个节点都有 previous，O(1) 就能拿到。
2. 哈希表里为什么存节点，而不是直接存 value？ 只存 value 的话，get 命中后不知道这个 key 在链表的哪个位置，还得在链表里找，O(n)。存节点引用，就能直接拿到节点，O(1) 摘下来挪到最前面。
3. 如果要求淘汰“使用次数最少”的（LFU），这个结构哪里不够用？ LRU 只按“最近一次使用的时间”排序，一条链表就够。LFU 要先比使用次数，次数相同再比时间。常见做法是给每个使用次数建一条双向链表，再记录当前的最小次数，淘汰时从“最小次数”那条链表的尾部删。
