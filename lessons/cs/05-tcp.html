第 5 课 · TCP：三次握手、四次挥手与可靠传输

IP 只管把分组尽力送到对面的主机，会丢、会乱序。TCP 在两端各记一套编号，靠「对方确认收到了哪里」来发现丢失并重发，于是在不可靠的网络上做出了一条可靠的字节流。握手、挥手、窗口，都是围绕这套编号展开的。

开始前要会：第 4 课的五层模型、封装与首部、端口号、IP 地址，以及「分组在网络里可能丢失、可能乱序到达」；第 1 课 · 进程间通信里的套接字。

还是那家小网店。顾客在浏览器里打开网店首页：浏览器所在的电脑临时挑了一个端口 52000，去连网店服务器的 443 端口（HTTPS）。这一课从头到尾只跟着这一条连接：它怎么建立、请求和响应怎么可靠地送达、最后怎么关掉，以及网络拥堵时它怎么放慢速度。

本课的路线：传输层干什么 → UDP：最简单的传输 → TCP 的四个特点 → TCP 首部 → 序号与确认号 → 三次握手 → 为什么不是两次 → 四次挥手 → TIME_WAIT → 确认与重传 → 滑动窗口与流量控制 → 拥塞控制 → 动手玩 → 题单怎么考。

1. 传输层干什么：从主机到进程

第 4 课讲过，网络层（IP）负责把一个分组从一台主机送到另一台主机。但一台主机上同时跑着很多进程：网店服务器上既有监听 443 的网店程序，也有监听 22 的 SSH 服务。分组到了服务器，该交给哪个进程？这就是传输层的事。

传输层：五层模型里网络层之上、应用层之下的那一层。它负责进程到进程的通信：用端口号区分同一台主机上的不同进程。网络层只负责主机到主机。

第 1 课提到的套接字就是进程使用传输层的入口。一条连接由两端的「IP 地址 + 端口」一起确定，共四个数：

（顾客电脑的 IP, 52000）  ↔  （网店服务器的 IP, 443）

服务器的 443 是固定的（大家都知道 HTTPS 去 443 找）；浏览器这边的 52000 是操作系统临时分配的，叫临时端口，每开一条新连接换一个。所以同一台服务器的 443 端口能同时和成千上万个顾客保持连接，靠的是对方的 IP 和端口各不相同。

传输层有两个主角：简单的 UDP 和复杂的 TCP。先看简单的。

2. UDP：只加端口，别的什么都不管

UDP（用户数据报协议）在应用的数据前面加一个 8 字节的首部，然后直接交给 IP。它的特点用一句话说：除了端口和校验，什么都不管。

  • 无连接：发之前不用和对方打招呼，想发就发。
  • 不可靠：丢了就丢了，不重发；乱序了也不排序。
  • 首部只有 8 字节：源端口、目的端口、长度、校验和，各 2 字节。校验和是按数据内容算出的一个数，接收方再算一遍，对不上就说明传输中出了错，直接丢弃。
  • 面向报文：应用交下来一条消息，UDP 就原样发一个数据报，不拆也不合。

为什么还有人用这么「简陋」的协议？因为快、开销小：不用建立连接，没有重传带来的等待。适合的场景：

场景为什么用 UDP
DNS 查询（53 端口，第 4 课）一问一答各一个小数据报，丢了让应用自己再问一次就行，建连接反而更慢
视频通话、直播、在线游戏要的是「新」，晚到的旧画面重发过来也没用
DHCP（自动分配 IP）、SNMP（网络管理）报文小、一问一答
HTTP/3（第 6 课）在 UDP 之上自己实现可靠传输，绕开 TCP 的一些限制

网店首页可不能这样：网页少了一段就显示不出来。所以浏览器和网店之间用的是 TCP。

3. TCP 的四个特点

TCP（传输控制协议）是传输层的另一个主角。HTTP、HTTPS、SSH、FTP、SMTP（第 4 课那些常用端口）全都跑在 TCP 上。它的四个特点：

面向连接：传数据之前，双方要先交换几个报文，商量好初始编号、各自分配好缓冲区（内存里暂存收发数据的一块区域），这个约定好的「通话状态」叫连接。用完还要专门把连接关掉。
可靠：发出去的数据保证不丢、不重、按顺序交给对方的应用。丢了会重发，重复的会丢掉，乱序的会排好。
面向字节流：TCP 不管应用一次写了多少，只把数据看成一长串字节，自己决定怎么切块发送。应用写一次 1000 字节，对方可能分两次读到 600 + 400。
全双工：一条连接上，两个方向可以同时发数据。可以理解为两条方向相反、各自独立的字节流。

TCP 传送的数据单位叫报文段（第 4 课「各层的数据单位」里的「段」）：TCP 首部 + 切下来的一块数据。下面先看首部里有什么，因为整课的机制都写在这几个字段里。

4. TCP 首部：几个关键字段

字段作用
源端口、目的端口各 16 位，找到两端的进程（和 UDP 一样）
序号 seq这个报文段里第一个数据字节的编号（下一节细讲）
确认号 ack「我期望收到你的下一个字节的编号」，只有 ACK 标志为 1 时才有效
窗口「我的接收缓冲区还能放多少字节」，用来做流量控制（第 11 节）
SYN同步（synchronize）：请求建立连接，并告诉对方自己的初始序号
ACK确认：确认号字段有效。连接建立后，所有报文段的 ACK 都是 1
FIN结束（finish）：我这个方向的数据发完了，要关闭
RST重置（reset）：出错了，立刻中断连接（例如连一个没人监听的端口）

PSH（让对方尽快把数据交给应用）和 URG（配合紧急指针，标出紧急数据）考得少，知道名字即可。

5. 序号与确认号：TCP 的核心

TCP 是字节流，所以它给自己发出的每一个字节都编一个号。两个方向各编各的。

初始序号（ISN）：建立连接时，每一方随机选一个起始编号。本课约定：客户端（浏览器）ISN = 100，服务器 ISN = 300。真实系统里是随机的 32 位数，这里用小数字方便算。
序号 seq：报文段里第一个数据字节的编号。
确认号 ack：期望收到的下一个字节的编号。ack = 201 的意思是「200 号以及之前的字节我都收到了，下一个请发 201」。这种「确认到哪里为止全部收到」的方式叫累计确认。

还有一条规则必须记住：SYN 和 FIN 虽然不带数据，但各占一个序号；只带 ACK、不带数据的报文段不占序号。为什么？因为 SYN 和 FIN 也需要被确认（对方得回一个 ack 表示「你的 SYN 我收到了」），占了一个号才有东西可确认。

由此得到笔试里最常用的公式：

收到 seq = x、带 n 字节数据的报文段后，回 ack = x + n
收到 SYN 或 FIN（seq = x，不带数据）后，回 ack = x + 1

6. 三次握手：建立连接

连接要商量好什么？最关键的是双方的初始序号：客户端得告诉服务器「我从 100 开始编号」，服务器得确认收到；反过来服务器也要告诉客户端「我从 300 开始」，客户端也得确认收到。这一来一回共要传四件事，其中服务器的「确认」和「告诉自己的 ISN」可以合在一个报文里，于是正好三个报文：

逐个看，每一步都套上一节的公式：

  1. 第一次：客户端发 SYN=1, seq=100。告诉服务器「我要连，我的 ISN 是 100」。发出后客户端进入 SYN_SENT（已发出 SYN，等回音）。
  2. 第二次：服务器回 SYN=1, ACK=1, seq=300, ack=101。ack = 100 + 1，因为 SYN 占了一个序号；seq = 300 是服务器自己的 ISN。服务器收到 SYN 时进入 SYN_RCVD（已收到 SYN）。
  3. 第三次：客户端回 ACK=1, seq=101, ack=301。seq = 101，因为客户端的 100 号已经被 SYN 用掉了；ack = 300 + 1。客户端收到第二次握手时就进入 ESTABLISHED（连接已建立），服务器收到第三次握手后也进入 ESTABLISHED。

这里出现的状态名都是 TCP 规定的，笔试会直接考：

状态意思谁会处于
CLOSED没有连接双方的起点和终点
LISTEN在某个端口上等别人来连服务器（程序调用了 listen()）
SYN_SENT发了 SYN，等 SYN+ACK客户端（程序调用了 connect()）
SYN_RCVD收到 SYN、回了 SYN+ACK，等最后的 ACK服务器
ESTABLISHED连接已建立，可以收发数据双方

两个常考细节：

  • 第三次握手的 ACK 可以携带数据（这时它就占序号了）；前两次不能带数据。
  • 主动发起连接的一方叫主动打开（客户端），在 LISTEN 状态等待的一方叫被动打开（服务器）。

7. 为什么是三次，不是两次

两次（SYN、SYN+ACK）之后，服务器就知道「客户端能发、我能收、我能发」，但还不知道客户端到底收没收到我的 SYN+ACK，也就是客户端是否确认了服务器的 ISN 300。少了这一步，最典型的问题出在已经作废的旧 SYN 上。

设想浏览器以前发过一个 SYN（seq = 50），它在某个拥堵的路由器里滞留了很久。浏览器等不到回音早就放弃了。现在这个旧 SYN 终于到了服务器：

归纳起来，三次握手的目的是：双方都确认了对方的初始序号（同步序号），并且都确认了「对方能收、也能发」。两次只能做到一半；四次可以，但第二、三次能合并，所以三次就够了。

SYN 洪泛攻击

服务器收到 SYN 后会进入 SYN_RCVD，并为这个「半建立」的连接分配一点资源，等第三次握手。攻击者用大量伪造的源 IP 狂发 SYN，却从不回第三次握手的 ACK，服务器里就堆满了 SYN_RCVD 状态的半连接，存放它们的队列（半连接队列）被占满，正常顾客的 SYN 就进不来了。这叫 SYN 洪泛（SYN Flood），是一种拒绝服务攻击（目的不是偷数据，而是让正常用户用不了服务）。常见防御是 SYN Cookie：收到 SYN 时先不分配资源，把必要信息编码进自己的初始序号里，等对方带着正确的 ack 回来再建立连接。

8. 四次挥手：关闭连接

浏览器拿到了首页，要关掉这条连接。第 3 节说过 TCP 是全双工的，两个方向是两条独立的字节流，所以要分别关：每个方向各需要一个 FIN 和一个 ACK，一共四个报文。

接着主线：握手后浏览器发了 100 字节的请求（101～200），服务器回了 200 字节的响应（301～500）。所以此刻客户端下一个序号是 201，服务器下一个序号是 501。

  1. 第一次：浏览器发 FIN=1, seq=201，表示「我没有数据要发了」，进入 FIN_WAIT_1（等对方确认我的 FIN）。
  2. 第二次：服务器回 ACK=1, ack=202（FIN 占了 201），进入 CLOSE_WAIT（等自己这边的程序关闭）。浏览器收到后进入 FIN_WAIT_2（等对方的 FIN）。
  3. 第三次：服务器的程序处理完剩下的事、调用 close() 后，发 FIN=1, seq=501，进入 LAST_ACK（等最后一个 ACK）。注意 seq 还是 501：第二次挥手是纯 ACK，不占序号。
  4. 第四次：浏览器回 ACK=1, seq=202, ack=502，进入 TIME_WAIT；服务器收到后进入 CLOSED。

为什么要四次，不能像握手那样把中间两个合并？握手时服务器收到 SYN 就能立刻回 SYN+ACK，因为它没有别的事要做。挥手时服务器收到 FIN，只说明浏览器不发了，服务器自己可能还有数据没发完，必须等它的程序处理完、调用 close() 才能发 FIN。所以 ACK 先回（让对方别重发 FIN），FIN 后发。中间这段「一个方向关了、另一个方向还开着」的状态叫半关闭。（如果服务器收到 FIN 时恰好也没东西要发，第二、三次可以合并成一个 FIN+ACK，变成三次挥手，这是允许的。）

服务器上出现大量 CLOSE_WAIT 说明什么？CLOSE_WAIT 是「对方已经关了，在等我自己的程序调用 close()」。这个状态不会超时自己消失，堆积很多，几乎总是服务器程序的 bug：收到对方关闭后没有关闭套接字（例如异常分支里忘了 close）。这和 TIME_WAIT 多是两回事。

9. TIME_WAIT：为什么要等 2MSL

MSL（报文段最大生存时间）：一个报文段在网络里最多能存活多久，超过就一定已经被丢弃。RFC 建议 2 分钟，Linux 实际取 30 秒，TIME_WAIT 固定等 60 秒。

主动关闭方发出最后一个 ACK 后，不立刻 CLOSED，而是在 TIME_WAIT 里等 2MSL。理由有两条。

理由一：最后一个 ACK 可能丢。它一旦丢了，服务器在 LAST_ACK 里等不到确认，会超时重发 FIN（发出的报文段一段时间没被确认就再发一次，叫超时重传，第 10 节细讲）。浏览器必须还「在场」才能再回一个 ACK：

为什么是 2MSL？最坏情况：ACK 在路上走了将近 1 个 MSL 才丢，服务器重发的 FIN 又要走将近 1 个 MSL 才到。等满 2MSL，就能覆盖「一来一回」。

理由二：让旧连接的报文在网络里死光。如果浏览器立刻用同一个端口 52000 再连网店 443，新连接和旧连接的四元组完全相同。旧连接还在路上滞留的报文段晚到了，可能被误认成新连接的数据。等 2MSL，两个方向上旧连接的所有报文段都过期了。

代价是：TIME_WAIT 期间这个四元组不能复用。主动关闭的一方才会进入 TIME_WAIT。如果是服务器主动关连接（例如短连接的 HTTP 服务），服务器上就会堆很多 TIME_WAIT，这本身是正常现象，可以通过让客户端主动关闭、改用长连接（第 6 课）或打开端口复用选项缓解。

10. 可靠传输：确认、超时重传、快速重传

回到连接建立之后。IP 不保证送达，TCP 靠下面三样东西把丢失、重复、乱序都处理掉：

  • 确认：接收方每收到数据就回 ack（第 5 节的累计确认）。
  • 按序号整理：接收方按 seq 把乱序到达的报文段排好；seq 已经收过的（重复的）直接丢弃。
  • 重传：发送方发现某段数据没被确认，就再发一次。怎么「发现」，有两种办法。
RTT（往返时间）：发出一个报文段到收到它的确认，一共花多久。
超时重传：发送方每发出一个报文段就启动一个重传计时器，时长叫 RTO（重传超时时间），比 RTT 稍长一些，由 TCP 根据测到的 RTT 动态调整。计时器到期还没收到确认，就认为它丢了，重发。

超时重传的毛病是慢：RTO 比 RTT 长，丢一个报文段就要干等一整个 RTO。于是有了更快的办法。为了看清楚，这一节把网店的响应换成更大的商品页：500 字节，分成 5 个报文段，每段 100 字节，seq 依次是 301、401、501、601、701。其中 401 那段丢了：

快速重传：发送方连续收到3 个重复 ACK（同一个 ack 值又来了 3 次，加上第一次共 4 个），就认定那一段丢了，立即重传，不等超时。

为什么是 3 个而不是 1 个？因为 IP 会乱序：401 可能只是比 501 晚到一点，这时也会出现 1～2 个重复 ACK。连续 3 个重复，基本可以肯定是真丢了。

11. 滑动窗口与流量控制

如果发一段就停下来等它的确认，一个 RTT 只能发一段，太慢了。TCP 允许发送方不等确认，连续发出一批，这一批的范围就是窗口。

接收窗口（rwnd）：接收方在每个报文段首部的「窗口」字段里告诉对方：我的接收缓冲区还能放多少字节。
发送窗口：发送方「已发出但还没被确认」加上「还可以马上发」的那段字节范围。发送窗口不能超过对方通告的 rwnd。

还是服务器发商品页（100 字节一段）。假设浏览器通告 rwnd = 400：

流量控制：接收方用 rwnd 限制发送方的速度，防止发得太快把接收方的缓冲区撑爆。管的是「两端之间」：接收方来不及处理。

如果浏览器的应用一直不读，缓冲区满了，它会通告 rwnd = 0，服务器就停止发送。之后浏览器腾出空间会发一个新的窗口通告，但万一这个通告丢了，双方会互相干等。所以收到零窗口的一方会启动持续计时器（也叫坚持计时器），定期发一个很小的零窗口探测报文，问「现在有空间了吗」。

补充一种笔试常见的分类：发送方只重传丢失那一段的叫选择重传（SR）；一旦超时就把那一段之后已发的全部重传的叫回退 N（GBN）。TCP 主要靠累计确认，行为接近 GBN，但会缓存乱序到达的数据，加上 SACK 选项（选择确认：接收方在首部选项里告诉发送方自己额外收到了哪几段不连续的数据）后接近选择重传。

12. 拥塞控制：别把网络堵死

流量控制只看接收方。可是中间的路由器也有限度：大家都猛发，路由器的缓冲区排满，分组就被丢弃；丢了大家重发，网络更堵。这种「网络里的分组太多，导致性能急剧下降」叫拥塞。

拥塞控制：发送方根据网络状况（主要看有没有丢包）主动调整发送速度，防止把网络堵死。管的是「整个网络」，和流量控制管的对象不同。
拥塞窗口（cwnd）：发送方自己估计的「网络现在能承受一次发多少」。笔试里以报文段个数为单位（每个报文段的数据量取最大报文段长度 MSS）。真正的发送窗口 = min(rwnd, cwnd)。
慢启动门限（ssthresh）：一条分界线。cwnd 小于它时快速增长，达到它之后改为缓慢增长。

本节以轮次（1 个 RTT 算 1 轮）为单位看 cwnd 怎么变。TCP Reno 的规则分四条：

  1. 慢启动：连接刚建好，cwnd = 1。每收到一个确认 cwnd 加 1，一轮里发出的 cwnd 个报文段都被确认，所以效果是每轮翻倍：1、2、4、8……名字叫「慢」，是因为起点只有 1，其实增长是指数级的。本课约定：翻倍后不超过 ssthresh，到达 ssthresh 就停在那里。
  2. 拥塞避免：cwnd ≥ ssthresh 以后，每轮只加 1，小心地试探网络的上限。
  3. 超时（说明网络很可能堵得厉害，连后续的报文段都过不去）：ssthresh = 当时 cwnd / 2，cwnd = 1，重新慢启动。
  4. 收到 3 个重复 ACK（说明后面的报文段还能到，网络只是轻微拥塞）：先快速重传丢的那一段，然后 ssthresh = 当时 cwnd / 2，cwnd = ssthresh，直接进入拥塞避免。这一步叫快恢复。

cwnd / 2 遇到奇数向下取整，且 ssthresh 最小取 2。拥塞避免的「加 1」和出事时的「减半」合起来，叫加法增大、乘法减小（AIMD）。早期的 TCP Tahoe 没有快恢复，3 个重复 ACK 时也把 cwnd 降到 1；题目没说明时按 Reno 算。

自测

1. 客户端初始序号为 1000，服务器初始序号为 5000。第三次握手报文的 seq 和 ack 分别是多少？ seq = 1001，ack = 5001。第一次握手 SYN 用掉了客户端的 1000 号，所以客户端下一个序号是 1001；服务器的 SYN（seq = 5000）也占一个序号，客户端期望的下一个是 5001。和本课主线 100 / 300 → 101 / 301 是同一个道理。
2. 主机甲向乙发送了一个 seq = 200、携带 300 字节数据的报文段，乙正确收到后，回给甲的确认号是多少？ 500。这段数据占 200～499 号字节，乙期望的下一个字节是 200 + 300 = 500。
3. 四次挥手中，主动关闭方在发出最后一个 ACK 后处于什么状态？要等多久？A. CLOSE_WAIT，1MSL　B. TIME_WAIT，2MSL　C. LAST_ACK，2MSL　D. FIN_WAIT_2，1MSL B。最后的 ACK 可能丢失，对方会重发 FIN，主动关闭方要还在场才能再回 ACK；ACK 走一程、重发的 FIN 再走一程，最长约 2MSL。同时这段时间也让旧连接的报文段全部过期。CLOSE_WAIT 和 LAST_ACK 是被动关闭方的状态。
4. 网店服务器上用 netstat 看到几千个 CLOSE_WAIT 连接，最可能的原因是？ 服务器程序在对方关闭连接后，没有调用 close() 关闭自己的套接字（通常是代码里某个分支漏了关闭）。CLOSE_WAIT 是被动关闭方收到 FIN 之后、自己发 FIN 之前的状态，只有程序调用 close 才会离开它。
5. 下列哪个协议通常使用 UDP？A. HTTP　B. SMTP　C. DNS　D. FTP C。DNS 查询一问一答，报文小，用 UDP 53 端口；建立 TCP 连接反而多花一个 RTT。其余三个都基于 TCP。
6. TCP Reno，初始 cwnd = 1，ssthresh = 8，第 6 轮发生超时。第 11 轮的 cwnd 是多少？ 6。逐轮：第 1～4 轮 1、2、4、8（第 4 轮到达 8 = ssthresh）；第 5 轮 9，第 6 轮 10，此时超时：ssthresh = 10 / 2 = 5，cwnd = 1。第 7 轮 1，第 8 轮 2，第 9 轮 4，第 10 轮本该翻倍成 8，但不超过 ssthresh = 5，所以是 5；第 11 轮进入拥塞避免，5 + 1 = 6。可以在动画里把 ssthresh 设为 8、N 设为 6 验证。
7. TCP Reno 中 cwnd = 20 时收到 3 个重复 ACK，接下来 ssthresh 和 cwnd 各变为多少？下一轮呢？ ssthresh = 20 / 2 = 10，cwnd = 10（快恢复，不回到 1），下一轮进入拥塞避免，cwnd = 11。如果是超时，则 ssthresh 同样是 10，但 cwnd = 1，下一轮 2。
8. 下列关于流量控制和拥塞控制的说法，正确的是？A. 流量控制是为了防止网络拥塞　B. 拥塞窗口由接收方通告　C. 发送窗口取接收窗口和拥塞窗口中较小的那个　D. 慢启动阶段 cwnd 线性增长 C。A 错：流量控制防的是接收方缓冲区溢出。B 错：接收方通告的是 rwnd，cwnd 是发送方自己估计的。D 错：慢启动每轮翻倍，是指数增长，拥塞避免才是线性增长。
