第 3 课 · 并发、锁与死锁

多个线程同时改同一份数据会出错，所以要加锁，让它们一个一个来。可锁用得不对，线程之间又会互相等对方放手、谁也动不了，这就是死锁。

开始前要会：第 1 课里的线程（同一进程的线程共享全局变量，各有自己的寄存器）、阻塞状态、上下文切换，以及进程间通信那张表里预告的「信号量」。第 2 课本课基本用不到。

还是那家小网店。服务器上的网店进程开了很多线程，每个线程服务一位顾客。这天，某款商品只剩最后 1 件，两位顾客几乎同时点了「下单」。两个线程会不会把这一件卖两次？本课从这个问题出发，一路讲到锁、信号量、死锁，最后用银行家算法给网店的后台任务分配资源。

本课的路线：竞态（卖最后一件）→ 临界区与互斥 → 互斥锁 → 信号量与 P/V → 生产者-消费者 → 哲学家就餐 → 死锁（两把锁互相等）→ 四个必要条件 → 资源分配图 → 预防 / 避免 / 检测 → 安全状态与银行家算法 → 至少要几个资源 → 动手玩 → 题单怎么考。

1. 竞态：两个线程卖最后一件商品

网店进程里有一个全局变量 stock，记着这款商品的库存，现在是 1。全局变量放在进程的数据区里，第 1 课讲过，同一进程的所有线程共享它。每个下单线程执行同样的代码：

if (stock > 0) {         // 检查：还有货吗
    stock = stock - 1;   // 扣库存
    创建订单;
}

看上去 stock = stock - 1 只是一行，CPU 却要分三步做，因为 CPU 只能对寄存器里的数做运算：

  1. 读：把内存里 stock 的值读进本线程的寄存器，记作 r；
  2. 减：r = r − 1，这一步只改寄存器，内存里的 stock 没变；
  3. 写：把 r 写回内存里的 stock。

每个线程有自己的一套寄存器（第 1 课），所以 T1 的 r 和 T2 的 r 是两个不同的数。而线程随时可能被时钟中断换下 CPU（多核时两个线程甚至真的同时在跑），所以两个线程的这几步可以按任意顺序交错。下面是一种很不走运的交错：

如果 T1 把四步做完、T2 再开始，T2 检查时会看到 0，提示「已售罄」，结果完全正确。错误只在某些交错下出现，所以这种 bug 时有时无、很难复现。

竞态条件（race condition）：多个线程（或进程）并发地读写同一份共享数据，最终结果取决于它们执行的先后交错顺序。

本课后面说的「线程」，换成「进程」道理完全一样（多个进程通过共享内存共用数据时也会竞态）。教材和考题多用「进程」这个词，本课两种说法混用。

2. 临界区与互斥

要治竞态，就得保证：T1 在「检查、读、减、写」这一段里时，T2 不能插进来动 stock。先给几个名词：

临界资源：一次只允许一个线程使用的资源，例如这里的 stock，或者一台打印机。
临界区：每个线程里访问临界资源的那段代码。注意临界区是代码，不是资源本身。这里就是从检查到写回那几行。
互斥：同一时刻最多只有一个线程在临界区里执行。

为了做到互斥，每个线程的代码都按下面的四段来组织：

一个合格的互斥机制要满足四条准则，选择题常考：

准则意思
空闲让进临界区里没人时，想进的线程应该马上能进
忙则等待临界区里有人时，别的线程必须等（这就是互斥本身）
有限等待想进的线程等待的时间必须有上限，不能永远进不去（不能饥饿）
让权等待进不去时应该让出 CPU（进入阻塞状态），不要占着 CPU 空转。这一条是「应该」，不是「必须」

原子操作：为什么不能自己用一个变量当门闩

最自然的想法：设一个变量 busy，进门前 while (busy) {} 等它变成 0，然后 busy = 1。可这本身又是「先检查、再修改」两步：T1 看到 busy 是 0、还没来得及改成 1 就被换下，T2 也看到 0，两人一起进门。门闩自己也竞态了。

原子操作：执行过程不会被打断的操作。要么还没开始，要么一次做完，别的线程看不到它做了一半的样子。

所以 CPU 专门提供了原子指令，例如 TestAndSet（读出旧值并把它设成 1，一条指令完成）、CAS（比较并交换：「如果现在是 0 就改成 1」一次完成）。锁就是用这些原子指令搭起来的。

3. 互斥锁

互斥锁（mutex）：一个只有「空闲」和「被占用」两种状态的对象，提供两个操作。lock()：锁空闲就占住它并返回；被别人占着就等。unlock()：放开锁，如果有人在等，让其中一个拿到。lock 和 unlock 本身都是原子的。
lock(stock_lock);         // 进入区
if (stock > 0) {          // ┐
    stock = stock - 1;    // │ 临界区
    创建订单;             // ┘
}
unlock(stock_lock);       // 退出区

现在 T2 想在 T1 的临界区中间插进来，会卡在 lock 上，等 T1 unlock 之后才能进去检查，这时它看到的是 0。「拿不到锁时怎么等」有两种做法：

  • 阻塞：线程进入阻塞状态，让出 CPU，锁放开时由内核把它唤醒（回到就绪队列）。满足「让权等待」，但睡下和唤醒都要上下文切换。
  • 自旋：线程一直循环检查锁是否空闲，叫忙等，这种锁叫自旋锁。不满足「让权等待」，白占 CPU；但不用切换，在多核上、而且临界区很短时反而更快。

4. 信号量与 P/V 操作

互斥锁只能表达「最多 1 个」。网店的数据库只允许同时开 3 个连接，第 4 个想连的线程得等别人用完，这就需要能数数的工具。

信号量（semaphore）：内核维护的一个整数 S，加上一个等在它上面的线程队列（等待队列）。只能用下面两个原子操作来改它，不能直接赋值。
P(S):  S = S - 1;
       if (S < 0)  本线程阻塞，排进 S 的等待队列;

V(S):  S = S + 1;
       if (S <= 0) 从 S 的等待队列里唤醒一个线程（让它进入就绪状态）;

P 是「申请一个」，V 是「归还一个」。名字来自荷兰语，也常写作 wait(S) / signal(S)。V 里的条件是 S <= 0：加 1 之后还不大于 0，说明加之前 S 是负的，也就是有人在排队，所以要叫醒一个。

把网店的 3 个数据库连接交给信号量 S 管理，初值 3。线程 T1～T5 依次执行 P(S)：

接着 T1 用完连接，执行 V(S)：S 从 −2 变成 −1，−1 ≤ 0，于是唤醒队头的 T4，T4 拿到 T1 让出的那个连接。T4 不需要再做一次 P，它当初那次 P 已经把账记上了。

这就引出一道常考的计算：信号量的取值范围。n 个线程共享 m 个资源，信号量初值 m。没人用时最大，是 m；n 个线程全都做了 P、还没人做 V 时最小，是 m − n。本例 m = 3、n = 5，取值范围是 −2 ～ 3。

信号量的初值决定了它的用途，记住三种：

初值用途网店里的例子
1互斥：当锁用，P 是加锁，V 是解锁保护 stock：P(mutex); 检查、扣库存; V(mutex);
n资源计数：同一种资源有 n 个3 个数据库连接，初值 3
0同步：规定先后顺序，「B 必须等 A 做完某件事」发货线程必须等下单线程把订单写好

互斥那一行走一遍：mutex = 1。T1 做 P，1 → 0，不小于 0，进入临界区；T2 做 P，0 → −1，阻塞；T1 出来做 V，−1 → 0，0 ≤ 0，唤醒 T2；T2 进入临界区，出来做 V，0 → 1，回到初始状态。

同步那一行也走一遍。设信号量 written 初值 0：下单线程写完订单后做 V(written)，发货线程发货前先做 P(written)。

  • 发货线程先跑到：P 把 0 变成 −1，阻塞。下单线程写完做 V，−1 → 0，唤醒发货线程。
  • 下单线程先写完：V 把 0 变成 1。发货线程来做 P，1 → 0，不阻塞，直接发货。

两种情况下，发货都发生在写好订单之后。口诀：同步信号量，「前面那件事」做 V，「后面那件事」做 P。

5. 生产者-消费者：P 的顺序不能颠倒

网店的下单线程把新订单放进一个订单缓冲区（只有 3 格的数组），发货线程从里面取订单去发货。放数据的一方叫生产者，取数据的一方叫消费者。要满足三件事：缓冲区满了，生产者得等；缓冲区空了，消费者得等；放和取都要改这个数组，不能同时进行。用三个信号量分别管：

生产者（下单线程）消费者（发货线程）
while (true) {
    生成一个订单;
    P(empty);   // 要一个空格
    P(mutex);
    放进缓冲区;
    V(mutex);
    V(full);    // 订单数 +1
}
while (true) {
    P(full);    // 要一个订单
    P(mutex);
    取出一个订单;
    V(mutex);
    V(empty);   // 空格数 +1
    发货;
}

考点在于：每一方都要先 P 资源信号量（empty 或 full），再 P(mutex)。如果生产者写反了，先 P(mutex) 再 P(empty)，在缓冲区已满时一步步推演（满时 empty = 0、full = 3、mutex = 1）：

毛病出在第 2 步：生产者占着 mutex 去等空格。正确的顺序是先确认有空格（P(empty)），再去占 mutex，这样占着 mutex 的线程一定马上能干完活并放开。同理，消费者写成先 P(mutex) 再 P(full)，在缓冲区为空时也会死锁。

V 的顺序则可以随便换：V 从不阻塞，换了顺序只会让别人早一点或晚一点被唤醒，不会卡住谁。

6. 哲学家就餐

另一个经典问题，常以选择题出现：5 位哲学家围着圆桌，每两人之间放 1 根筷子，共 5 根。吃饭要同时拿到左右两根。

常见的三种解法，每种都是把这个「圈」拆掉：

  1. 最多只许 4 人同时去拿筷子（用一个初值为 4 的信号量）。5 根筷子分给 4 个人，至少有一人能拿到两根，吃完放下，别人就能接着吃。
  2. 奇数号先拿左边、偶数号先拿右边。相邻两人会先抢同一根，抢不到的那位手里什么也没拿，不会形成一圈。
  3. 只有左右两根都空闲时，才一次拿起两根（把「检查并拿两根」放进临界区）。

7. 死锁：两把锁互相等

回到网店。为了让「下单」和「取消订单」互不干扰，程序里有两把互斥锁：库存锁保护 stock，订单锁保护订单表。两个线程各要两把锁，但拿的顺序不一样：

T1：下单T2：取消订单
lock(库存锁);   // 先扣库存
lock(订单锁);   // 再写订单
……
unlock(订单锁);
unlock(库存锁);
lock(订单锁);   // 先把订单改成「已取消」
lock(库存锁);   // 再把库存加回去
……
unlock(库存锁);
unlock(订单锁);

不走运的交错：T1 拿到库存锁，正要拿订单锁时被换下；T2 上来拿到订单锁，接着去要库存锁，发现在 T1 手里，阻塞；T1 回来要订单锁，发现在 T2 手里，也阻塞。

死锁：一组线程（或进程）中的每一个，都在等待只有这组里另一个成员才能释放的资源，结果全都无法继续推进。没有外力干预，它们会永远等下去。

和第 1 课说的饥饿区分开：饥饿是某个线程一直轮不到（别人还在正常运行），换个时机可能就轮到了；死锁是一组线程全部卡住，而且永远不会自己解开。上一节生产者-消费者写反、哲学家各拿左筷子，都是死锁。

8. 死锁的四个必要条件

把上面三个死锁放在一起看，它们都同时具备下面四条。反过来，只要有一条不成立，就不会死锁，所以这四条叫死锁的必要条件。

注意「必要」不是「充分」：四条都满足也不一定死锁（在资源有多个实例时，见下一节）。但单个实例的资源（例如一把锁）下，出现循环等待就一定死锁。

9. 资源分配图

题目常把资源的占用情况画成一张图，让你判断有没有死锁。这张图叫资源分配图，规则如下：

  • 圆圈表示线程（进程），方框表示一类资源，方框里的每个黑点是这类资源的一个实例（例如 3 个数据库连接就画 3 个点）。
  • 请求边：线程 → 资源，表示「这个线程在等这类资源的一个实例」。
  • 分配边：资源里的某个点 → 线程，表示「这个实例已经分给了这个线程」。

判断规则：

  • 图里没有环：一定没有死锁。
  • 有环，且环上每类资源都只有 1 个实例：一定死锁。
  • 有环，但资源有多个实例：可能死锁，也可能不。要用化简来判断：找一个请求都能被满足的线程（例如右图的 T3），假设它跑完、放回所有资源，擦掉它的边；再找下一个……能把所有边都擦掉，就没有死锁；擦到某一步再也找不到，剩下的线程就是死锁的。右图依次擦掉 T3、T1、T2，所以不死锁。

10. 对付死锁的四种办法

办法什么时候动手怎么做
预防写程序 / 设计系统时让四个必要条件中的某一条永远不成立（见下）
避免每次分配资源前先算一算：这次分了以后，系统还安不安全？不安全就先不给。代表是银行家算法（第 11 节）
检测与解除死锁发生之后平时随便分配；定期用资源分配图化简等办法检测，发现死锁就解除：撤销（杀掉）其中一个或几个线程、或者抢占它们的资源、或者把它们回滚到之前的某个状态
忽略不管认为死锁极少发生，出了事重启。Windows、Linux 对普通程序的锁就是这样（叫「鸵鸟策略」）

预防具体破坏哪一条：

  • 破坏互斥：通常做不到，锁的意义就是互斥。
  • 破坏占有并等待：一次性申请全部资源，拿不全就一个也不拿。缺点是资源被长时间闲占，利用率低。
  • 破坏不可抢占：申请新资源失败时，把手里已有的全部放掉，以后重新申请。实现复杂，已做的工作可能白费。
  • 破坏循环等待：给所有资源编号，规定只能按编号从小到大申请（叫有序资源分配法）。网店里只要规定「所有线程都先拿库存锁、再拿订单锁」，T2 就会先在库存锁上排队，手里什么也没有，圈就成不了。这是实际编程最常用的办法。

死锁预防和死锁避免的区别常考：预防是事先立规矩，四个条件之一根本不可能出现；避免不限制申请方式，四个条件都可能出现，只是每次分配前算一下，绕开会走向死锁的那条路。

11. 安全状态与银行家算法

网店后台每晚跑 5 个任务 P0～P4（导出报表、同步物流、清理缓存……），它们要用三类资源：

资源类是什么系统总量
A数据库连接10
B工作线程5
C缓存槽7

每个任务启动时声明「我最多会同时要多少」，之后边跑边一点点申请。银行家算法用四张表（每行一个任务，每列一类资源，写成向量 (A, B, C)）：

Max：任务声明的最大需求。Allocation：此刻已经分给它的。Need：它还可能再要的，Need = Max − Allocation。Available：系统里还没分出去的，= 总量 − 所有 Allocation 之和。

两个向量比大小，规定为每一个分量都满足才算：(1,2,2) ≤ (3,3,2) 成立；(7,4,3) ≤ (3,3,2) 不成立，因为 7 > 3。

任务AllocationMaxNeed = Max − Allocation
P0(0,1,0)(7,5,3)(7,4,3)
P1(2,0,0)(3,2,2)(1,2,2)
P2(3,0,2)(9,0,2)(6,0,0)
P3(2,1,1)(2,2,2)(0,1,1)
P4(0,0,2)(4,3,3)(4,3,1)
合计(7,2,5)

Available = (10,5,7) − (7,2,5) = (3,3,2)。

安全状态

安全序列：把所有任务排成一个顺序 <Pa, Pb, …>，使得按这个顺序，每个任务的 Need 都能用「当时空闲的资源 + 排在它前面的任务跑完后放回的资源」满足。安全状态：至少存在一个安全序列的状态。否则叫不安全状态。

直观地说：安全状态就是「哪怕每个任务都把 Need 要满，系统也有办法排个先后，让大家全部跑完」。任务拿够 Max 后一定会在有限时间内跑完并放回全部 Allocation，这是银行家算法的前提。

安全性检查：怎么找安全序列

设一个向量 Work 表示「此刻手头可用的资源」，初值 = Available，再给每个任务一个「已完成」标记，初值都是「否」。然后反复做：

  1. 从 P0 开始往后扫，找第一个未完成、且 Need ≤ Work 的任务；
  2. 找到了：假设它拿到资源跑完，放回 Allocation：Work = Work + Allocation，标为已完成，写进序列，回到第 1 步（又从 P0 扫起）；
  3. 扫完一遍都找不到：停。如果全部任务都已完成，状态安全；否则不安全。

注意第 2 步加的是 Allocation，不是 Need：任务跑完放回的是它全部持有的东西（Allocation + 刚借给它的 Need），而借给它的 Need 本来就是从 Work 里出的，一出一进抵消，净增的就是 Allocation。

按这个规则，在本例上逐轮推一遍：

轮Work从 P0 起扫描选中Work + Allocation
1(3,3,2)P0 (7,4,3)：A 7 > 3 ✗；P1 (1,2,2) ≤ (3,3,2) ✓P1(3,3,2) + (2,0,0) = (5,3,2)
2(5,3,2)P0 ✗（7 > 5）；P1 已完成；P2 (6,0,0)：6 > 5 ✗；P3 (0,1,1) ✓P3(5,3,2) + (2,1,1) = (7,4,3)
3(7,4,3)P0 (7,4,3) ≤ (7,4,3) ✓（相等也算）P0(7,4,3) + (0,1,0) = (7,5,3)
4(7,5,3)P0、P1 已完成；P2 (6,0,0) ✓P2(7,5,3) + (3,0,2) = (10,5,5)
5(10,5,5)只剩 P4 (4,3,1) ✓P4(10,5,5) + (0,0,2) = (10,5,7)

全部完成，安全序列是 <P1, P3, P0, P2, P4>。最后的 Work 等于总量 (10,5,7)，正好可以用来检查有没有算错。

安全序列不唯一，换一种扫描规则就会得出别的序列。例如「找到一个后从它的下一个接着扫」会得到 <P1, P3, P4, P0, P2>，教材上还常见 <P1, P3, P4, P2, P0>，它们都对。做选择题时，把选项里的序列逐个按上表的方法验证即可；本页和下面的动画统一用「每轮从 P0 开始，选第一个满足的」。

资源请求：给不给

某个任务 Pi 发来请求向量 Request，系统按四步处理：

  1. Request ≤ Need[i]？不满足，说明它要的超过了自己声明的最大值，出错，拒绝。
  2. Request ≤ Available？不满足，说明现在空闲的资源不够，Pi 等待。
  3. 试分配：Available −= Request，Allocation[i] += Request，Need[i] −= Request。
  4. 对试分配后的状态做安全性检查。安全：批准，试分配正式生效。不安全：拒绝，把第 3 步的修改全部撤回，Pi 等待。

用三个请求各走一遍：

① P1 请求 (1,0,2)（从初始状态出发）。(1,0,2) ≤ Need[1] = (1,2,2) ✓；(1,0,2) ≤ Available = (3,3,2) ✓。试分配：Available = (2,3,0)，Allocation[1] = (3,0,2)，Need[1] = (0,2,0)。安全性检查：第 1 轮 Work = (2,3,0)，P0 ✗，P1 (0,2,0) ✓，Work = (2,3,0) + (3,0,2) = (5,3,2)，此后和上表第 2～5 轮完全一样。得到安全序列 <P1, P3, P0, P2, P4>，批准。

下面两个请求都发生在P1 的请求已经批准之后，此时 Available = (2,3,0)。

② P4 请求 (3,3,0)。(3,3,0) ≤ Need[4] = (4,3,1) ✓；(3,3,0) ≤ Available = (2,3,0)？A 类 3 > 2 ✗。资源不够，P4 等待，连试分配都走不到。

③ P0 请求 (0,2,0)。(0,2,0) ≤ Need[0] = (7,4,3) ✓；(0,2,0) ≤ (2,3,0) ✓。试分配：Available = (2,1,0)，Need[0] = (7,2,3)。安全性检查，Work = (2,1,0)：

  • P0 Need (7,2,3)：A 7 > 2 ✗
  • P1 Need (0,2,0)：B 2 > 1 ✗
  • P2 Need (6,0,0)：A 6 > 2 ✗
  • P3 Need (0,1,1)：C 1 > 0 ✗
  • P4 Need (4,3,1)：A 4 > 2 ✗

第一轮就一个也找不到，状态不安全，拒绝，撤回试分配，P0 等待。这里资源明明「够分」，却不能分：分了以后，B 类只剩 1 个、C 类一个不剩，没有任何任务能保证跑完。这正是「避免」和「检测」的不同：银行家算法在可能出事之前就拒绝了。

银行家算法的缺点也常考：要事先知道每个任务的最大需求，任务数和资源数要固定，每次分配都要做一遍 O(m·n²) 的检查（m 类资源、n 个任务），所以实际系统很少用，主要出现在考题里。

12. 至少要几个资源才不会死锁

高频计算题：n 个进程，每个最多需要 k 个同类资源，系统至少要有多少个资源，才保证不会死锁？

用网店的例子推：3 个导出任务（n = 3），每个最多同时需要 4 个数据库连接（k = 4）。

  1. 先找最坏情况：资源被分得最「平均」、每个任务都差一个。每个任务拿 k − 1 = 3 个，3 个任务共占 n(k − 1) = 9 个。
  2. 如果总共只有 9 个，此时一个空闲的都没有，每个任务都在等第 4 个：死锁。所以 9 个不够。
  3. 如果有 10 个，最坏情况下还剩 1 个空闲。不管给了谁，那个任务都凑齐了 4 个，能跑完，放回 4 个；剩下的任务接着就能凑齐。所以 10 个够了。
  4. 再看「不是最坏」的分法：如果有任务拿得多于 3 个，它已经凑齐、能跑完；拿得少于 3 个，空闲的就更多。都不会比最坏情况更糟。

所以答案是 n(k − 1) + 1。本例 3 × (4 − 1) + 1 = 10。

题目也会反着问，都从「n(k − 1) + 1 ≤ 资源总数 m」这个不等式解：

  • m = 8 个资源，每个进程最多要 3 个，最多允许几个进程？n × 2 + 1 ≤ 8，n ≤ 3.5，所以最多 3 个。验算：3 个进程最坏占 6 个，还剩 2 个，不会死锁；4 个进程最坏占 8 个，一个不剩，会死锁。
  • m = 4 个资源，3 个进程，每个进程最多能要几个？3(k − 1) + 1 ≤ 4，k ≤ 2，所以最多 2 个。

自测

1. 全局变量 x 初值 0，两个线程各执行一次 x = x + 1，不加锁。结束后 x 可能是多少？ 可能是 1 或 2。每个线程分读、加、写三步。如果一个做完三步另一个才开始，结果是 2；如果两个都先读到 0、各自算出 1 再写回，后写的覆盖先写的，结果是 1。不可能是 0（至少有一次写回了 1），也不会大于 2。
2. 4 个进程共享 2 台打印机，用信号量 S 管理。S 的初值和取值范围是多少？S = −1 表示什么？ 初值 2（资源计数）。没人用时最大是 2；4 个进程全做了 P 时最小是 2 − 4 = −2，所以范围是 −2 ～ 2。S = −1：2 台打印机都被占了，还有 1 个进程在等待队列里。
3. 生产者-消费者问题中，把下面哪一处交换后可能导致死锁？A. 生产者的 P(empty) 和 P(mutex)　B. 生产者的 V(mutex) 和 V(full)　C. 消费者的 V(mutex) 和 V(empty) A。交换后生产者先占住 mutex，缓冲区满时再在 P(empty) 上阻塞；消费者要先拿 mutex 才能取订单、做 V(empty)，于是两边互相等。B、C 交换的都是 V，V 不会阻塞，最多让对方晚一点被唤醒。
4. 系统有 4 个进程，每个最多需要 3 台同类设备。至少要配几台设备才保证不会死锁？ 4 × (3 − 1) + 1 = 9。最坏情况每个进程各拿 2 台，占掉 8 台、都在等第 3 台；第 9 台给谁，谁就能跑完并放回 3 台。
5. 系统有 6 台同类设备，每个进程最多需要 2 台。最多允许几个进程并发，保证不会死锁？ n × (2 − 1) + 1 ≤ 6，n ≤ 5，最多 5 个。验算：5 个进程各拿 1 台，还剩 1 台，给谁谁就能跑完；6 个进程各拿 1 台就一台不剩，死锁。
6. 「规定所有线程必须按资源编号从小到大申请资源」破坏的是死锁的哪个必要条件？「一次性申请全部资源」呢？ 前者破坏循环等待：大家都按同一个顺序拿，等待关系只会从小号指向大号，不可能绕回来成圈。后者破坏占有并等待：拿不全就一个都不拿，不会出现手里拿着又去等的情况。
7. 用本课的银行家数据（初始状态，Available = (3,3,2)），如果 P4 一上来就请求 (3,3,0)，能批准吗？ 不能。(3,3,0) ≤ Need[4] = (4,3,1) ✓，(3,3,0) ≤ Available ✓，可以试分配：Available 变成 (0,0,2)，Need[4] 变成 (1,0,1)。安全性检查，Work = (0,0,2)：P0 (7,4,3)、P1 (1,2,2)、P2 (6,0,0) 的 A 类都大于 0；P3 (0,1,1) 的 B 类 1 > 0；P4 (1,0,1) 的 A 类 1 > 0。一个也找不到，不安全，拒绝。
8. 判断：「系统处于不安全状态就一定会发生死锁」「资源分配图里有环就一定死锁」。 都错。不安全状态只是「没法保证」，任务不一定真把 Need 要满，可能侥幸不死锁；但死锁状态一定是不安全的。资源分配图有环时，只有环上每类资源都是单实例才一定死锁，多实例时要化简才能判断（见第 9 节右图）。
