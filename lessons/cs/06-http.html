第 6 课 · HTTP：请求、响应与状态码

浏览器和网店之间说的「话」就是 HTTP：浏览器发一份请求报文，服务器回一份响应报文，响应的第一行用一个三位数的状态码告诉浏览器结果如何。本课把这两份报文拆开看，再看每个常见状态码是谁、为什么返回的。

开始前要会：第 4 课（五层模型与封装、端口号 80 / 443、IP 地址、DNS 把域名解析成 IP）、第 5 课（TCP 是面向连接的可靠字节流、三次握手、UDP 无连接）。

还是那家小网店。顾客在家里的电脑（192.168.1.23）上打开浏览器，访问 https://shop.example.com/products/42 看一个商品（42 号商品「帆布托特包」，89 元），然后登录，再下单。第 4 课讲了数据怎么找到网店服务器（198.51.100.80），第 5 课讲了怎么建立一条可靠的 TCP 连接。这一课讲连接建好之后，浏览器和网店具体说了什么。全课就跟着这位顾客的这三件事走。

本课的路线：从输入网址到看到页面（总览）→ URL 的结构 → 请求报文和响应报文 → 方法、安全与幂等 → GET 和 POST 的区别 → 无状态与 Cookie / Session → 网店的架构：反向代理 → 状态码五大类 → 301 与 302 → 304 与缓存 → 4xx：401 与 403 → 5xx：502 与 504 → HTTP 的版本 → HTTPS → 动画 → 题单怎么考。

1. 总览：从输入网址到看到页面

先定几个名词：

客户端与服务器：主动发起请求的一方叫客户端（这里是顾客的浏览器），等着别人来请求、给出回复的一方叫服务器（这里是网店）。
HTTP（超文本传输协议）：浏览器和网站之间的应用层协议。它规定通信只有一种模式：客户端发一个请求，服务器回一个响应，一问一答。服务器不会主动给浏览器发东西。
资源：服务器上能用一个地址找到的东西：一个网页、一张图片、一条订单都是资源。HTML 是写网页用的标记语言，例如 <h1>帆布托特包</h1> 表示一个大标题。浏览器把 HTML 画成你看到的页面，这一步叫渲染。

顾客按下回车后，浏览器依次做这六件事：

  1. DNS 查询：浏览器只知道名字 shop.example.com，先问 DNS 服务器要到 IP 198.51.100.80（第 4 课）。
  2. TCP 三次握手：网址开头是 https，默认端口是 443，于是浏览器和 198.51.100.80:443 建立 TCP 连接（第 5 课）。HTTP 跑在 TCP 上，因为它要求报文一个字节都不能错、不能少。
  3. TLS 握手：TLS 是夹在 HTTP 和 TCP 之间的一层加密协议。双方先验证网店的身份，再商量出一把只有它俩知道的密钥，之后的 HTTP 报文都加密传输（第 14 节）。网址是 http 开头时没有这一步。
  4. 发 HTTP 请求：浏览器写一份请求报文：「我要 /products/42 这个资源」（第 3 节）。
  5. 服务器处理：网店程序从数据库查出 42 号商品，拼成 HTML，写进响应报文发回（第 7 节讲网店内部的分工）。
  6. 渲染：浏览器解析 HTML，发现里面还引用了图片、样式文件，就在同一条连接上继续请求它们（第 13 节），全部到齐后把页面画出来。

先补一个衡量快慢的单位：RTT（往返时间）是一个小报文从浏览器到服务器、再回到浏览器所用的时间。上面 ①②③④ 各要等对方回话，每一步都至少花 1 个 RTT。后面讲 HTTP 版本时，会用 RTT 来比较谁快。

2. URL：一个网址由哪几部分组成

URL（统一资源定位符）：资源的地址，也就是俗称的网址。它说清楚了三件事：用什么协议、找哪台机器上的哪个进程、要那个进程里的哪个资源。

把网址写完整一点，就能看到所有的部分：

部分例子作用
协议（scheme）https用什么协议。它决定了默认端口：http 是 80，https 是 443
主机shop.example.com哪台机器。交给 DNS 解析成 IP
端口:443那台机器上的哪个进程。和协议默认端口一样时可以省略
路径/products/42服务器上的哪个资源。会原样写进请求报文的第一行
查询参数?color=red附加的参数，格式是 名=值，多个之间用 & 连接，例如 ?color=red&size=L
片段#reviews页面里的某个位置（例如跳到「评论」那一段）。不会发给服务器，只由浏览器自己处理

URL 里只能直接写英文字母、数字和少数符号。中文、空格等要先转成 % 加十六进制字节的形式，叫 URL 编码，例如空格写成 %20。

3. 请求报文和响应报文

第 4 课说过，应用层的数据单位叫报文。HTTP/1.1 的报文是纯文本，人可以直接读。下面就是浏览器为了看 42 号商品发出的请求报文原文：

GET /products/42 HTTP/1.1
Host: shop.example.com
User-Agent: Mozilla/5.0
Accept: text/html
Accept-Language: zh-CN
Connection: keep-alive

网店回的响应报文原文：

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 84
Cache-Control: max-age=60
ETag: "p42-v3"
Last-Modified: Sat, 21 Nov 2026 08:00:00 GMT

<!doctype html>
<title>帆布托特包</title>
<h1>帆布托特包</h1>
<p>¥89</p>

两份报文的结构是一样的，都分成四部分：

请求行：请求报文的第一行，由三项组成，用空格隔开：方法（要对资源做什么，这里 GET 表示「获取」，第 4 节细讲）、路径（/products/42）、协议版本（HTTP/1.1）。
状态行：响应报文的第一行，也是三项：协议版本、状态码（三位数字，200）、原因短语（给人看的说明，OK）。程序只看状态码，第 8 节起细讲。
首部（header，也叫头部）：若干行 名字: 值，补充说明这次请求或响应。名字不区分大小写。
空行和正文（body，也叫主体）：首部结束后是一个空行，空行之后就是正文，也就是真正要传的数据：网页、图片、表单内容等。

为什么要有空行和 Content-Length？第 5 课讲过，TCP 是字节流，它只保证字节按顺序到达，不会替你标出「一份报文到哪里结束」。所以 HTTP 自己定规矩：读到空行，就知道首部结束了；再按 Content-Length 读够那么多字节，就知道正文结束了。

注意 Content-Length 数的是字节，不是字符。上面的正文有 63 个字符，但按 UTF-8 编码，「帆布托特包」每个汉字占 3 个字节（出现了两次，共 10 个汉字），¥ 占 2 个字节，所以是 63 − 10 − 1 + 10 × 3 + 2 = 84 字节。

常考的首部：

首部出现在作用
Host请求要访问哪个域名。HTTP/1.1 里必须有：一台服务器（一个 IP）上可以同时放好几个网站，只看 IP 分不出你要哪个，要靠 Host 区分（这叫虚拟主机）
User-Agent请求客户端是什么软件（哪种浏览器）
Accept请求客户端能接受什么类型的内容
Content-Type都有正文是什么类型：text/html（网页）、application/json（JSON 数据）、image/png 等
Content-Length都有正文的字节数
Connection都有keep-alive 表示响应完不要关 TCP 连接，close 表示关（第 13 节）
Cookie / Set-Cookie请求 / 响应第 6 节
Location响应让浏览器去哪个新地址（第 9 节）
Cache-Control、ETag、Last-Modified响应缓存用（第 10 节）

4. 方法：要对资源做什么

请求行的第一项是方法。同一个路径，配不同的方法，意思就不一样。网店用到的五个：

方法含义网店里的例子
GET获取资源GET /products/42：看 42 号商品
POST提交数据，让服务器处理（常用来新建）POST /orders：下一个新订单
PUT用请求里的内容整个替换资源（没有就新建）PUT /products/42，正文写价格 79：把 42 号商品改成 79 元
DELETE删除资源DELETE /orders/1001：取消 1001 号订单
HEAD和 GET 一样，但服务器只回状态行和首部，不回正文只想知道商品页多大、有没有改过，不想下载整页

另外还有 PATCH（只改资源的一部分）和 OPTIONS（问服务器「这个资源支持哪些方法」），了解即可。

判断方法有两个性质，笔试很爱考：

安全：这个方法不会改变服务器上的数据，只是读。GET、HEAD、OPTIONS 是安全的。
幂等：同一个请求执行 1 次和执行很多次，服务器上的最终结果一样。

拿网店逐个看「连发三次」会怎样：

请求发 3 次之后安全？幂等？
GET /products/42什么都没改是是
PUT /products/42（价格 79）价格是 79，和发 1 次一样否是
DELETE /orders/1001订单没了，和发 1 次一样（后两次会回「找不到」，但服务器上的数据没再变）否是
POST /orders下了 3 个订单否否

记住：安全的一定幂等（什么都不改，执行多少次都一样），反过来不成立。POST 既不安全也不幂等。这就是为什么刷新一个刚提交过订单的页面时，浏览器会弹窗问「要重新提交表单吗」：它知道 POST 重发可能会再下一单。网络出错时，浏览器和代理可以放心地自动重试幂等的请求，但不会自动重试 POST。

5. GET 和 POST 的区别

这是题单里最常见的一题。看两份真实的报文：顾客按颜色筛选商品用 GET，下单用 POST。

区别按重要程度排：

GETPOST
语义（根本区别）获取资源提交数据让服务器处理
安全 / 幂等安全、幂等都不是
参数放哪通常放在 URL 的查询参数里通常放在正文里
能不能缓存默认可以被浏览器缓存（第 10 节）默认不缓存
历史记录、书签完整 URL 会留在历史记录里，可以收藏正文不会留下；收藏的只是地址
刷新 / 后退无害，直接重发浏览器会提示「重新提交表单」
长度限制HTTP 协议本身没有限制。GET 的限制来自浏览器和服务器对 URL 长度的限制（常见几 KB 到几十 KB）；POST 的正文一般可以很大

几个常见的错误说法，选择题里常拿来当干扰项：

  • 「POST 比 GET 安全。」不对。参数在正文里只是不显示在地址栏，报文在网上传的时候一样是明文，抓包就能看到。真正防止被偷看要靠 HTTPS（第 14 节）。这里的「安全」也和第 4 节「安全方法」的意思不同，别混。
  • 「GET 不能带正文，POST 不能带查询参数。」都不绝对。POST /orders?from=app 完全合法；GET 带正文协议没禁止，但没有规定它的意义，很多服务器会忽略，所以不要这么用。
  • 「POST 一定发两个 TCP 报文段，GET 发一个。」不是协议规定，是个别客户端的实现细节。

6. 无状态，以及 Cookie 和 Session

无状态：HTTP 协议本身不记得之前的请求。每个请求都是独立的，服务器处理第二个请求时，并不知道它和第一个请求来自同一个人。

无状态让服务器简单：不用为每个顾客保存什么，任何一台服务器都能处理任何一个请求。但网店需要「记住」顾客：登录以后再下单，服务器得知道下单的是谁。解决办法是让浏览器每次都带上一个「号码牌」：

Cookie：服务器在响应里用 Set-Cookie 首部交给浏览器的一小段数据（名=值）。浏览器把它存下来，以后每次请求同一个网站时，都自动放进 Cookie 首部带回去。
Session（会话）：服务器为每个登录的顾客保存的一份数据（是谁、购物车里有什么等），存在服务器上。每份 session 有一个随机生成的编号，叫 session ID。服务器只把这个编号放进 Cookie 交给浏览器。
CookieSession
存在哪浏览器服务器
大小每个约 4 KB 以内没有这个限制，由服务器决定
安全性用户能看到、能改，不要放密码等敏感信息用户看不到内容，只拿到一个随机编号
关系Session 通常依赖 Cookie 来传递 session ID。如果浏览器禁用了 Cookie，可以把 session ID 写进 URL（URL 重写），但这样容易泄露

Set-Cookie 后面那几个属性：HttpOnly 表示网页里的脚本读不到这个 Cookie（防止被恶意脚本偷走）；Secure 表示只在 HTTPS 连接上发送；Max-Age=3600 或 Expires=… 规定多久后过期，不写就是关掉浏览器即失效。

7. 网店的架构：反向代理

到目前为止，我们把「网店服务器」当成一个整体。要看懂 5xx 状态码是谁返回的，得看清它里面的分工。网店服务器上跑着三个进程：

反向代理：挡在应用前面的一台服务器。客户端以为自己在和网站说话，其实只连到了代理；代理再把请求转给后面真正干活的应用，把应用的响应转回给客户端。本课的反向代理是一个叫 nginx 的常用软件。
上游（upstream）：代理把请求转给的那个服务器，这里就是 shop-server。
网关：HTTP 状态码里说的「网关」，指的就是这种替客户端去找上游要结果的中间服务器。反向代理就是一种网关。

为什么要多这一层？nginx 帮应用做了几件通用的事：

  • 处理 HTTPS：TLS 的加解密在 nginx 上做完，shop-server 收到的已经是普通 HTTP。
  • 负载均衡：可以在后面放好几个 shop-server，把请求轮流分给它们。
  • 限流、缓存静态文件：请求太多时直接挡掉一部分（第 12 节的 503）；图片、样式文件直接由 nginx 回，不打扰应用。

与之相对的正向代理是替客户端出面的代理，例如公司网络里所有员工上网都经过的那台代理。正向代理隐藏的是客户端，反向代理隐藏的是服务器。

8. 状态码的五大类

状态码：响应状态行里的三位数字，告诉客户端这次请求的结果。第一位数字决定大类，后两位是这一类里的细分。

常考的状态码（网店里的例子在动画里都能点出来）：

状态码含义网店里什么时候出现
100 Continue首部收到了，可以接着发正文上传大文件前先问一句（了解即可）
200 OK成功正常打开商品页
201 Created成功，并新建了一个资源POST /orders 下单成功，首部 Location: /orders/1001 指向新订单
204 No Content成功，但响应没有正文DELETE /orders/1001 取消成功，没什么要回的
206 Partial Content只返回了资源的一部分请求里带 Range: bytes=0-1023，只要商品视频的前 1024 字节（断点续传、视频拖动进度条）
301 / 302永久 / 临时重定向第 9 节
304 Not Modified没改过，用你的缓存第 10 节
400 Bad Request请求格式不对，服务器看不懂下单的 JSON 少了一个括号
401 / 403没认证 / 没权限第 11 节
404 Not Found资源不存在访问 /products/999，没有这个商品
405 Method Not Allowed资源存在，但不支持这个方法用 GET 访问只收 POST 的 /orders

9. 重定向：301 和 302

重定向：服务器不直接给资源，而是告诉浏览器「去另一个地址拿」。响应的状态码是 3xx，新地址写在 Location 首部里。浏览器收到后自动向新地址再发一次请求，顾客只会看到地址栏变了。

网店以前用的是 /item.php?id=42 这种网址，改版后统一换成 /products/42。可是搜索引擎、顾客的书签里还存着旧网址。nginx 上配一条规则，凡是旧网址，直接回：

HTTP/1.1 301 Moved Permanently
Location: https://shop.example.com/products/42
Content-Length: 0

301 和 302 的流程完全一样，区别只在「这个搬家是不是永久的」，而这决定了浏览器和搜索引擎以后怎么做：

301 Moved Permanently（永久）302 Found（临时）
意思旧地址作废了，以后都去新地址这次先去新地址，旧地址以后还用
浏览器会缓存这个跳转：下次访问旧地址，不再问服务器，直接去新地址不缓存，每次访问旧地址都要先问服务器
搜索引擎把旧地址的排名、收录转给新地址，以后只收录新地址继续收录旧地址
网店的例子改版换网址；http:// 统一跳到 https://；换域名没登录就访问「我的订单」，先临时跳到登录页，登录后再跳回来；商品临时下架时跳到活动页

如果把临时跳转错写成 301，浏览器记住了跳转，等你想恢复旧地址时，老顾客的浏览器还是会自己跳走，很难收回。所以拿不准就用 302。

补充两个：307 和 308 分别是 302 和 301 的「严格版」。历史上很多浏览器收到 301 / 302 后，会把原来的 POST 改成 GET 去请求新地址；307 / 308 规定方法和正文都不许变，原来是 POST 就还是 POST。

10. 304 与缓存

浏览器缓存：浏览器把拿到过的响应存在本机，下次要同一个资源时，尽量不再从网上下载。

第 3 节的响应里有三个首部就是为缓存准备的：

  • Cache-Control: max-age=60：这份副本 60 秒内都是新鲜的。60 秒内再访问，浏览器直接用本机副本，一个请求都不发，这叫强缓存。
  • ETag: "p42-v3"：服务器给这个版本的页面起的版本标签，内容一变，标签就变。
  • Last-Modified: Sat, 21 Nov 2026 08:00:00 GMT：这个资源最后修改的时间。

60 秒过了，副本不保证新鲜了，但多半没变。浏览器就带着版本标签去问一句「我手里这份还能用吗」，这叫协商缓存（也叫条件请求）：

服务器第一次给的浏览器下次带回的比较的是
Last-ModifiedIf-Modified-Since修改时间。精度只到秒，一秒内改两次分不出；内容没变只是时间变了也会误判为「改过」
ETagIf-None-Match版本标签。按内容算，更准；两个都有时优先看 ETag

要点：304 是 3xx，但它不是让你去别的地址，而是让你「回去用自己的缓存」，这种「重定向」指回本地。另外，强缓存命中时根本不发请求，浏览器的开发者工具里会显示 200（from cache），不是 304；只有发了条件请求、服务器确认没变，才是 304。

11. 4xx：401 和 403

4xx 表示「请求本身有问题」。最容易混的是 401 和 403，先分清两个词：

认证（authentication）：确认「你是谁」。网店靠 Cookie 里的 session ID 认人（第 6 节）。
授权（authorization）：确认「你能不能做这件事」。知道你是 alice 以后，还要看这条订单是不是 alice 的。

顾客看订单 GET /orders/1002 时，shop-server 依次过两关：

401 Unauthorized403 Forbidden
卡在哪一关认证：服务器不知道你是谁（没带凭证，或凭证过期、无效）授权：服务器知道你是谁，但你没有权限
重试有没有用有：登录拿到有效凭证再来，就可能成功没有：换个凭证登录同一个账号也没用，除非管理员给你加权限
网店的例子没登录（没带 Cookie）就请求 /orders/1001alice 登录了，却去看 bob 的 /orders/1002
响应里的特征协议要求带 WWW-Authenticate 首部，说明该怎么认证无特殊首部

名字有点误导：401 的原因短语叫 Unauthorized（未授权），但它说的其实是未认证。记法：401 = 你是谁？403 = 我知道你是谁，但不行。

两个实际中的变化：

  • 顾客在浏览器里点「我的订单」时，网店通常不回 401，而是回 302 跳到登录页（第 9 节），对人更友好。给程序调用的接口（例如 App 请求 /orders/1001）才直接回 401。
  • 有的网站对没权限的资源故意回 404 而不是 403，免得让人知道「这条订单是存在的」。

再对比一下另外三个 4xx：400 是请求的格式坏了（服务器看不懂）；404 是路径对应的资源不存在；405 是资源存在，但不支持这个方法（响应会带 Allow: POST 首部说明它支持哪些）。

12. 5xx：500、502、503、504

5xx 表示请求没问题，是服务器这边没办好。回到第 7 节的架构图，四个 5xx 恰好出在不同的位置：

状态码谁返回发生了什么典型原因
500 Internal Server Errorshop-server应用收到了请求，处理时自己出错代码 bug、空指针、未处理的异常
502 Bad Gatewaynginxnginx 从上游拿不到合法的响应：连不上，或者上游回了乱七八糟的东西、半路断了shop-server 进程挂了或在重启；端口配错
503 Service Unavailablenginx（或应用）服务器暂时不能处理：太忙或在维护。可以带 Retry-After: 30 告诉客户端 30 秒后再来过载限流、停机维护
504 Gateway Timeoutnginxnginx 把请求转给了上游，但上游在规定时间内没回响应慢 SQL、应用卡死、调用的外部服务太慢

502 和 504 怎么分：两个都是网关在抱怨上游，区别在「上游有没有及时回话」。

  • 502：上游回的话不对，或者根本连不上。通常很快就出现：nginx 去连 8080，被 RST 拒绝（第 5 课：对方端口上没有进程在监听时，会回 RST），马上就知道不行了。
  • 504：上游一直不回话。一定是等满了超时时间才出现（nginx 默认等 60 秒）。连接是通的，请求也送到了，只是 shop-server 迟迟没有写回响应。

排查时的思路因此也不同：看到 502，先查应用进程还在不在、端口对不对；看到 504，先查应用里什么操作慢（最常见的是数据库查询，第 8 课讲怎么用索引加速）。

500 和 503 怎么分：500 是应用出了 bug，原样重试多半还错；503 是暂时的，等一会儿再试就可能成功。

13. HTTP 的版本：1.0、1.1、2、3

网店的商品页除了 HTML，还引用了 4 张商品图片，一共 5 个资源，浏览器要发 5 个请求。下面只数 RTT（不算 DNS、TLS 和传数据本身的时间），看各版本加载它们要多久：

  • HTTP/1.0：默认非持久连接，每个请求单独建一条 TCP 连接，响应完就关。5 个资源 = 5 次握手 + 5 次请求 = 10 个 RTT，还要建 5 条连接。
  • HTTP/1.1：默认持久连接（长连接，Connection: keep-alive），一条 TCP 连接上可以接连发很多个请求。只握手 1 次：1 + 1 + 4 = 6 个 RTT。
    1.1 还允许管线化（pipelining）：不等上一个响应回来就发下一个请求。但响应必须按请求的顺序回，前面一个慢，后面的全被堵住，这叫队头阻塞。这个缺点让浏览器基本都没有开启管线化，改成对同一个网站开 6 条左右的并行连接。
  • HTTP/2：报文改成二进制格式，切成小块叫帧；每个请求-响应是一条流，有编号。不同流的帧可以在同一条连接上交错发送，接收方按编号重新拼起来，这叫多路复用。4 张图的请求一起发出，响应交错着回，谁也不用等谁：1 + 1 + 1 = 3 个 RTT。另外还有头部压缩（HPACK：连续请求里重复的首部，例如那一长串 User-Agent，只传一次，之后用编号代替）和服务器推送（了解即可）。
  • HTTP/3：HTTP/2 在 HTTP 这一层没有队头阻塞了，但底下的 TCP 还有：TCP 是一条字节流，丢了一个报文段，后面所有流的数据都要等它重传完才能交上去。HTTP/3 干脆不用 TCP，改用跑在 UDP 上的 QUIC 协议。QUIC 自己实现了可靠传输，并且每条流单独保证顺序，一条流丢包不影响别的流；它还把 TLS 合进了握手，建连更快；换网络（比如手机从 Wi-Fi 切到 4G）时连接不断。
版本传输层关键改进遗留问题
HTTP/1.0TCP—每个请求一条连接，握手开销大
HTTP/1.1TCP持久连接（默认）、管线化、Host 首部必填、断点续传（Range / 206）HTTP 层的队头阻塞
HTTP/2TCP二进制分帧、多路复用、头部压缩、服务器推送TCP 层的队头阻塞
HTTP/3UDP（QUIC）没有队头阻塞、建连快、连接迁移有的网络会拦 UDP

注意，不管哪个版本，方法、状态码、首部的含义都没变，变的只是报文在线上怎么编码、怎么传。前面讲的内容对所有版本都成立。

14. HTTPS：HTTP + TLS

普通 HTTP 是明文。顾客的请求要经过家用路由器、运营商的好几台路由器（第 4 课），路上任何一台机器都能读到里面的 Cookie: sid=7f3a9c，拿去冒充 alice；还能偷偷改响应，比如把收款账号换掉。HTTPS 就是在 HTTP 和 TCP 之间加一层 TLS，解决三件事：

  • 机密性：别人截到了也看不懂（加密）。
  • 完整性：别人改了一个字节也会被发现。
  • 身份认证：确认对面真的是 shop.example.com，不是冒充的（证书）。

默认端口也从 80 换成 443。加密用到两类方法：

对称加密：加密和解密用同一把密钥。速度快，适合加密大量数据。难点是：这把密钥怎么安全地交给对方？在网上明文传过去，就被偷看了。
非对称加密：每方有一对密钥：公钥公开给所有人，私钥只有自己有。用公钥加密的数据，只有对应的私钥能解开。不用事先共享秘密，但计算慢很多。

HTTPS 两样一起用：先用非对称加密，安全地商量出一把对称密钥（叫会话密钥）；之后的报文都用这把对称密钥加密。慢的只做一次，快的用来干大量的活。

还剩一个漏洞：浏览器收到一把公钥，怎么知道它真是网店的，而不是路上某台机器冒充网店塞过来的？这就是证书的作用：

证书：一份写着「shop.example.com 的公钥是这个」的文件，由证书颁发机构（CA）用 CA 自己的私钥签了名（数字签名：用私钥对内容的摘要做运算，任何人都能用对应的公钥验证「确实是它签的、内容没被改过」）。浏览器和操作系统里预装了可信 CA 的公钥，所以能验证签名。

为什么证书能防冒充？冒充者能把网店的证书原样转给浏览器，但没有网店的私钥，后面就商量不出会话密钥；冒充者用自己的公钥做一张证书，又没有 CA 的签名，或者域名对不上，第 ③ 步就会被浏览器发现。

几个常考的点：

  • HTTPS 不是一个新协议，HTTP 报文本身一点没变，只是交给 TLS 加密后再交给 TCP。所以请求行、首部、Cookie、正文都被加密了。
  • 加密的是内容。路上的人仍然能看到双方的 IP 地址和端口（它们在 IP 和 TCP 首部里，不加密），通常也能看到访问的域名，但看不到路径、Cookie 和正文。
  • HTTPS 比 HTTP 多一次 TLS 握手（TLS 1.3 多 1 个 RTT），加解密也有计算开销，这是它比 HTTP 慢一点的原因。

自测

1. 用户请求 https://shop.example.com/orders/1002，已登录，但这条订单属于别人。服务器最合适返回哪个状态码？A. 400　B. 401　C. 403　D. 404 C。服务器通过 Cookie 已经知道你是谁（认证通过），只是你没有权限看（授权失败）。401 用于「不知道你是谁」；404 也有网站这样用来隐藏资源的存在，但按状态码本意，选 403。
2. 用户访问网站时页面显示 502 Bad Gateway，最可能的原因是？A. 用户没有登录　B. 请求的页面不存在　C. 反向代理后面的应用服务器进程已停止　D. 应用服务器处理时间过长 C。502 是网关（反向代理）从上游拿不到合法响应，最常见的就是上游进程挂了、连不上。A 是 401，B 是 404，D 是 504：上游连得上，只是超时了还没回。
3. 下列 HTTP 方法中，不是幂等的是？A. GET　B. PUT　C. DELETE　D. POST D。POST /orders 发 3 次会下 3 个订单，结果和发 1 次不一样。PUT 把价格改成 79，发几次都是 79；DELETE 删一次和删多次，资源最后都不存在。
4. 关于 GET 和 POST，下列说法正确的是？A. POST 比 GET 安全，因为参数在正文里　B. HTTP 协议规定 GET 的 URL 不能超过 2 KB　C. GET 是安全且幂等的方法　D. POST 请求不能带查询参数 C。A 错：参数在正文里只是不显示在地址栏，不用 HTTPS 时抓包照样能看到。B 错：长度限制来自浏览器和服务器，协议本身没有。D 错：POST /orders?from=app 完全合法。
5. 浏览器发出带 If-None-Match: "p42-v3" 的请求，服务器发现资源的 ETag 仍是 "p42-v3"，会返回？响应里有正文吗？ 304 Not Modified，没有正文。条件成立说明浏览器手里的副本还是最新的，服务器只回状态行和首部，浏览器继续用本机缓存。如果 ETag 变了，就回 200 并带上新的完整正文。
6. 一个网页包含 1 个 HTML 和 4 张图片，只计 RTT（不计 DNS、TLS 和传输时间）。分别用 HTTP/1.0 非持久连接、HTTP/1.1 持久连接（不用管线化）、HTTP/2 多路复用，各需要几个 RTT？
  • 非持久：每个对象都要 1 个 RTT 握手 + 1 个 RTT 请求响应，5 × 2 = 10。
  • 持久、不管线化：握手 1 次（1）+ HTML（1）+ 4 张图逐个请求（4）= 6。
  • 多路复用：握手（1）+ HTML（1）+ 4 张图同时请求（1）= 3。HTML 必须先到，浏览器才知道要哪几张图，所以图片不能和 HTML 一起发。
7. 关于 HTTPS，下列说法错误的是？A. 默认端口是 443　B. 传输数据时主要使用对称加密　C. 证书用来证明服务器的公钥确实属于该域名　D. HTTPS 加密后，路上的路由器看不到通信双方的 IP 地址 D。IP 地址在 IP 首部里，路由器要靠它转发，不能加密。TLS 加密的是 HTTP 报文（请求行、首部、Cookie、正文）。B 对：非对称加密只用来商量会话密钥，之后用更快的对称加密。
8. HTTP/3 和前几个版本最大的不同是什么？为什么要这样改？ HTTP/3 的传输层不再是 TCP，而是基于 UDP 的 QUIC。原因是 HTTP/2 虽然在一条连接上多路复用，但 TCP 是一条字节流，丢一个报文段，所有流都要等它重传（TCP 层的队头阻塞）。QUIC 对每条流单独保证顺序，一条流丢包不影响其他流，还把 TLS 握手合进了建连过程。
