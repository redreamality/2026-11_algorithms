第 7 课 · SQL：查询语法与执行顺序

SQL 是向数据库「要数据」的语言：你只说要什么，不说怎么找。一条 SELECT 写的顺序是 SELECT … FROM … WHERE …，但数据库执行的顺序是 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。弄懂这个顺序，大部分语法题就都能推出来。

开始前要会：数据库部分从这一课开始，不需要网络课的知识。只用到第 1 课的进程：正在运行的程序。数据库软件本身也是服务器上的一个进程。

网店的数据都存在数据库里：有哪些顾客、卖哪些商品、谁买了什么。网店程序要显示「我的订单」「本月各城市销售额」时，就写一条 SQL 发给数据库。这一课只用一组小数据（6 个用户、5 种商品、8 笔订单），所有 SQL 都在它上面跑，每条都写出结果。

本课的路线：数据库和表 → 主键、外键与三张表 → SQL 的四类语句与约束 → 查询的基本写法 → NULL 的坑 → 聚合与分组 → 连接（JOIN）→ 执行顺序 → 动画 → 子查询 → UNION → 删除数据的三种方式 → 范式 → 题单怎么考。

1. 数据库、表、行、列

数据库：按一定结构长期存放数据的集合。网店的用户、商品、订单都放在里面。
数据库管理系统（DBMS）：管理数据库的软件，例如 MySQL、PostgreSQL、Oracle、SQLite。它在服务器上作为一个进程运行，别的程序把请求发给它，由它去读写磁盘上的数据。平时说「MySQL 数据库」，常常同时指这个软件和它管的数据。
关系型数据库：把数据组织成一张张表的数据库。上面四个都是。本课说的「数据库」都指关系型数据库。
表、行、列：表像一张电子表格。每一列（也叫字段）是一种属性，例如「名字」「城市」，有固定的类型（整数、文字、日期……）。每一行（也叫记录）是一个具体的东西，例如「张三，北京」。
SQL（Structured Query Language，结构化查询语言）：和关系型数据库打交道的标准语言。各家数据库在标准之上各有一点差别，叫方言。本课以 MySQL 为准，和 SQLite 不同的地方会顺带说明。

SQL 有一个和普通编程语言很不一样的地方：它是声明式的。你写「给我 11 月里各城市的销售额」，而不写「先打开订单表，一行一行读……」。具体怎么找，由 DBMS 自己决定。不过它决定之前，会先按一个固定的逻辑顺序理解你的 SQL，第 8 节专门讲这个顺序。

2. 主键、外键与网店的三张表

主键（PRIMARY KEY）：一张表里能唯一确定一行的列。主键的值不能重复，也不能为空。三张表都用 id 列作主键。
外键（FOREIGN KEY）：一张表里的某一列，它的值必须是另一张表主键里已有的值。订单表的 user_id 就是外键：它指向 users 表的 id，说明「这笔订单是谁下的」。

3. SQL 的四类语句与约束

SQL 语句按「对什么动手」分成四类，考题常问某个关键字属于哪一类：

注意 TRUNCATE 属于 DDL，而同样是删数据的 DELETE 属于 DML，第 12 节会说这个区别带来了什么后果。另外还有 COMMIT、ROLLBACK 这类管「事务」的语句，有时单独叫 TCL，第 9 课讲。

建表时的约束

约束：建表时给列定的规矩。DBMS 在每次写入时检查，不合规矩的 INSERT / UPDATE / DELETE 直接报错，数据就不会被写坏。

用 DDL 建订单表和用户表（MySQL 写法）：

CREATE TABLE users (
  id   INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(20) NOT NULL,
  city VARCHAR(20)                       -- 没写 NOT NULL，所以允许为 NULL
);
CREATE TABLE products (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(50) NOT NULL UNIQUE,
  price INT NOT NULL,
  stock INT NOT NULL DEFAULT 0
);
CREATE TABLE orders (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  user_id    INT NOT NULL,
  product_id INT NOT NULL,
  quantity   INT NOT NULL,
  created_at DATE NOT NULL,
  FOREIGN KEY (user_id)    REFERENCES users(id),
  FOREIGN KEY (product_id) REFERENCES products(id)
);
约束规矩在网店里会拦下什么
PRIMARY KEY唯一且非空；一张表只能有一个主键（但主键可以由几列合起来组成）再插一个 id = 1 的用户
UNIQUE不能重复，但可以有 NULL（MySQL 里允许多个 NULL）；一张表可以有多个再上架一个也叫「鼠标」的商品
NOT NULL必须填值插一个没有名字的用户
FOREIGN KEY值必须在被引用的表里存在插一笔 user_id = 99 的订单（没有 99 号用户）；删掉还有订单的张三
DEFAULT没给值时自动填的默认值不拦，只是上架新商品时没写库存就填 0

AUTO_INCREMENT（自增）不是约束，而是让 DBMS 自动给新行分配 id：上一个是 6，下一个就是 7。SQLite 里对应的写法是 INTEGER PRIMARY KEY（可再加 AUTOINCREMENT）。另一个差别：SQLite 默认不检查外键，要先执行 PRAGMA foreign_keys = ON；MySQL 默认的 InnoDB 存储引擎（MySQL 里实际负责把表存到磁盘上的那一部分，第 8 课细讲）默认就检查。

4. 查询的基本写法

最简单的查询是 SELECT 列 FROM 表：从哪张表（FROM）、取哪几列（SELECT）。SELECT * 表示取所有列。

结果集：一条 SELECT 返回的数据。它本身也是一张表（有列、有行），只是不存在磁盘上。所以一条查询的结果可以再拿来当表用，第 10 节的子查询就靠这一点。
别名（AS）：给列或表另起一个短名字。SELECT price * 0.8 AS sale 让结果集的这一列叫 sale；AS 可以省略。

WHERE：只要满足条件的行

WHERE 后面写一个条件，DBMS 对表里的每一行算一遍，条件为真的行才留下。条件可以用：

  • 比较：=、<>（不等于，也可以写 !=）、>、<、>=、<=。SQL 里判断相等只写一个等号。
  • 组合：AND（都要满足）、OR（满足一个就行）、NOT（取反）。AND 比 OR 先算：a OR b AND c 等于 a OR (b AND c)。拿不准就加括号。
  • IN (值1, 值2, …)：等于其中任何一个。是一串 OR 的简写。
  • BETWEEN 小 AND 大：在范围内，两头都包含。等于 >= 小 AND <= 大。
查询结果
SELECT name, price, stock FROM products WHERE price > 100 AND stock > 0;键盘 199 30；显示器 999 5（耳机贵但库存是 0）
SELECT name, price, stock FROM products WHERE price > 500 OR stock = 0;显示器 999 5；耳机 299 0
SELECT name FROM users WHERE city IN ('北京', '广州');张三、王五、赵六
SELECT name, price FROM products WHERE price BETWEEN 99 AND 299;键盘 199；鼠标 99；耳机 299（99 和 299 本身都算）

文字和日期要加单引号：'北京'、'2026-11-01'。

LIKE：按模式匹配文字

LIKE 用两个通配符描述「长什么样」的文字：% 匹配任意多个字符（包括 0 个），_ 匹配恰好一个字符。

MySQL 的 LIKE 对英文字母是否区分大小写取决于列的排序规则，默认的排序规则不区分；SQLite 的 LIKE 默认对 ASCII 字母也不区分。要匹配真正的 % 或 _ 字符，要在前面加反斜杠转义。

ORDER BY、LIMIT、DISTINCT

  • ORDER BY 列 [ASC | DESC]：按列排序，默认 ASC（从小到大），DESC 从大到小。可以写多列：ORDER BY city, id DESC 先按城市，城市相同再按 id 倒序。不写 ORDER BY 时，结果的顺序没有任何保证。
  • LIMIT n：只要前 n 行。LIMIT m, n（MySQL 写法）跳过 m 行再取 n 行，等价于 LIMIT n OFFSET m。注意逗号写法里先写的是跳过几行。SQL Server 用 TOP n，Oracle 老版本用 ROWNUM。
  • SELECT DISTINCT：去掉结果里完全重复的行。选了多列时，看的是这几列合起来是否重复。
查询结果
SELECT name, price FROM products ORDER BY price DESC LIMIT 3;显示器 999；耳机 299；键盘 199
SELECT name, price FROM products ORDER BY price DESC LIMIT 1, 2;耳机 299；键盘 199（跳过最贵的 1 个，再取 2 个）
SELECT DISTINCT city FROM users;北京、上海、广州、深圳、NULL，共 5 行（两个北京算一行；NULL 也算一行）

5. NULL：不是 0，也不是空字符串

NULL：表示「没有值 / 不知道」。周八的城市是 NULL，意思是不知道他在哪个城市。它和 0、和空字符串 '' 都不一样：库存是 0 表示「知道，就是没货」。

因为 NULL 是「不知道」，拿它做比较，结果也只能是「不知道」。SQL 的条件于是有三种结果：TRUE（真）、FALSE（假）、UNKNOWN（未知），这叫三值逻辑。关键规则：

  • NULL 和任何值比较（=、<>、>……），结果都是 UNKNOWN，包括 NULL = NULL。
  • WHERE 只留下结果为 TRUE 的行。FALSE 和 UNKNOWN 都被丢掉。
  • NULL 参与算术，结果还是 NULL：1 + NULL 是 NULL。

看一个容易写错的查询：「找出不在北京的用户」。

SELECT name FROM users WHERE city <> '北京';

判断是不是 NULL，只能用 IS NULL / IS NOT NULL：

查询结果
SELECT name FROM users WHERE city = NULL;0 行（不报错，但永远是 UNKNOWN）
SELECT name FROM users WHERE city IS NULL;周八
SELECT name FROM users WHERE city <> '北京' OR city IS NULL;李四、赵六、孙七、周八

三值逻辑里 AND、OR 的规则可以这样记：把 UNKNOWN 当成「可能真可能假」，看结果是否已经确定。FALSE AND UNKNOWN 一定是 FALSE；TRUE OR UNKNOWN 一定是 TRUE；TRUE AND UNKNOWN、FALSE OR UNKNOWN、NOT UNKNOWN 都还是 UNKNOWN。

两个常用工具：COALESCE(city, '未填') 返回第一个不是 NULL 的参数，可以把 NULL 换成默认值（MySQL 还有 IFNULL(city, '未填')）；MySQL 的 <=> 是「NULL 安全的等于」，NULL <=> NULL 为真。

6. 聚合与分组：COUNT、GROUP BY、HAVING

聚合函数

聚合函数：把很多行算成一个值的函数：COUNT（数个数）、SUM（求和）、AVG（平均）、MAX、MIN。除了 COUNT(*)，它们都会跳过 NULL。

最常考的是 COUNT 的三种写法，在 users 表上跑一遍：

SELECT COUNT(*) AS all_rows, COUNT(city) AS has_city, COUNT(DISTINCT city) AS cities FROM users;
写法数的是什么结果
COUNT(*)行数，不管列里是什么6
COUNT(city)city 不是 NULL 的行数（周八不算）5
COUNT(DISTINCT city)不同的、非 NULL 的 city 有几种（北京只算一次）4

COUNT(1) 和 COUNT(*) 结果一样：1 永远不是 NULL，所以每行都算。对比上一节：SELECT DISTINCT city 返回 5 行（含 NULL 那一行），而 COUNT(DISTINCT city) 是 4，因为 COUNT 不数 NULL。

在 products 表上：SUM(stock) = 30 + 50 + 5 + 0 + 100 = 185；AVG(price) = (199 + 99 + 999 + 299 + 49) ÷ 5 = 1645 ÷ 5 = 329；MAX(price) = 999；MIN(price) = 49。如果某列有 NULL，AVG 的分母只算非 NULL 的行，所以 AVG(列) 不一定等于 SUM(列) / COUNT(*)。

GROUP BY 分组，HAVING 筛组

分组（GROUP BY）：把某列取值相同的行归成一组，每组只输出一行，组里的数据用聚合函数算。GROUP BY user_id 就是「每个用户一组」。
SELECT user_id, COUNT(*) AS cnt, SUM(quantity) AS qty
FROM orders GROUP BY user_id;

分组以后，每组只剩一行，所以 SELECT 里只能写分组的列和聚合函数。比如 SELECT user_id, created_at … GROUP BY user_id：张三那组有两个日期，输出哪个？没法回答。MySQL 5.7 起默认开启 ONLY_FULL_GROUP_BY，这种写法直接报错；更老的 MySQL 和 SQLite 会随便挑组里一行的值，不报错。

HAVING：对分组之后的组做筛选，条件里可以用聚合函数。WHERE 则是在分组之前对行做筛选，条件里不能用聚合函数（那时还没分组，没东西可聚合）。

把两者放在一起：「11 月里下了至少 2 单的用户」。

SELECT user_id, COUNT(*) AS cnt
FROM orders
WHERE created_at >= '2026-11-01'     -- 先去掉 10 月的订单（行）
GROUP BY user_id
HAVING COUNT(*) >= 2;                -- 再去掉不到 2 单的用户（组）

不加 WHERE，只写 HAVING COUNT(*) >= 2，结果是用户 1、2、4。能用 WHERE 筛掉的就在 WHERE 里筛：先去掉的行越多，后面分组要处理的数据越少。

7. 连接（JOIN）：把几张表拼起来

「每笔订单是谁下的」，答案分在两张表里：订单在 orders，名字在 users。要把它们拼起来看，就要用连接。

连接（JOIN）：把两张表的行按某个条件配对，拼成一张更宽的表。配对条件写在 ON 后面，通常是「外键 = 主键」，例如 ON o.user_id = u.id。
笛卡尔积：不写任何配对条件时，左表的每一行和右表的每一行都拼一次。users 6 行、orders 8 行，得到 6 × 8 = 48 行。写法是 SELECT * FROM users, orders 或 users CROSS JOIN orders。所有连接都可以理解成「先做笛卡尔积，再按 ON 的条件挑出配对成功的行」（DBMS 实际不会真的先生成 48 行）。

两张表都有 id 列，所以要写清是谁的 id：FROM orders o 给 orders 起了表别名 o，o.user_id 就是「orders 表的 user_id 列」。

INNER JOIN 与 LEFT JOIN

  • INNER JOIN（内连接，JOIN 默认就是它）：只保留两边都配对成功的行。
  • LEFT JOIN（左外连接，也写 LEFT OUTER JOIN）：左表的行一个不少；某行在右表里找不到配对，就照样输出一行，右表的列全填 NULL。
SELECT u.name, o.id FROM users u LEFT JOIN orders o ON o.user_id = u.id;

LEFT JOIN 有两个经典用法，都用到了第 5、6 节的 NULL 规则：

  1. 找「没有对应记录」的行：配不上的行，右表列是 NULL，于是 
    SELECT u.id, u.name FROM users u LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
    结果只有 6 周八：从没下过单的用户。
  2. 统计每个用户的订单数，包括 0： 
    SELECT u.name, COUNT(o.id) AS n FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
    周八得 0。如果写成 COUNT(*)，周八会得 1：他那一行虽然右边全是 NULL，但它确实是一行，COUNT(*) 照数不误。

一个常见的坑：给右表加条件，写在 ON 里和写在 WHERE 里结果不同。

写法结果
… LEFT JOIN orders o ON o.user_id = u.id AND o.created_at >= '2026-11-10'6 行：每个用户都在，只配 11 月 10 日起的订单（赵六 6、孙七 7、李四 8；其余三人 o.id 为 NULL）
… LEFT JOIN orders o ON o.user_id = u.id WHERE o.created_at >= '2026-11-10'3 行：赵六 6、孙七 7、李四 8。补出来的 NULL 行在 WHERE 里得 UNKNOWN，被丢掉，LEFT JOIN 退化成了内连接

四种连接对比

  • A RIGHT JOIN B 等于 B LEFT JOIN A，所以实际中很少写 RIGHT JOIN。
  • MySQL 不支持 FULL OUTER JOIN，要用「LEFT JOIN 的结果 UNION RIGHT JOIN 的结果」模拟（UNION 见第 11 节）。SQLite 从 3.39 起支持 RIGHT JOIN 和 FULL JOIN，更老的版本两个都不支持。
  • 连接可以连好几次：orders o JOIN users u ON … JOIN products p ON …，先连出一张宽表，再连下一张。

8. 执行顺序：一条 SELECT 是怎么一步步算出来的

现在把前面的零件拼成一条完整的查询：「11 月里，各城市的销售额（件数 × 单价之和），只看超过 200 元的城市，按销售额从高到低取前两名」。

SELECT u.city, SUM(o.quantity * p.price) AS total
FROM orders o
  JOIN users u    ON o.user_id = u.id
  JOIN products p ON o.product_id = p.id
WHERE o.created_at >= '2026-11-01'
GROUP BY u.city
HAVING SUM(o.quantity * p.price) > 200
ORDER BY total DESC
LIMIT 2;
结果
citytotal
上海1195
北京496

写的时候 SELECT 在最前面，但 DBMS 不是从 SELECT 开始算的。它在逻辑上按下面的顺序处理，每一步的输入都是上一步产出的中间结果表：

在这条查询上，每一步做了什么（第 9 节的动画会把每张中间表画出来）：

  1. FROM orders：拿到 8 笔订单。
  2. JOIN users、JOIN products：每笔订单配上下单人的城市、商品的单价，还是 8 行，但列变多了。
  3. WHERE：订单 5（10 月 28 日）不满足条件，剩 7 行。
  4. GROUP BY u.city：7 行分成 4 组：北京（订单 1、2、4）、上海（3、8）、广州（6）、深圳（7）。
  5. HAVING：各组销售额：北京 199 + 198 + 99 = 496，上海 999 + 196 = 1195，广州 99，深圳 299。广州不超过 200，去掉，剩 3 组。
  6. SELECT：每组输出 city 和 total 两列，到这一步才有了别名 total。
  7. DISTINCT：这条查询没写，跳过。
  8. ORDER BY total DESC：上海 1195、北京 496、深圳 299。
  9. LIMIT 2：只要前两行：上海、北京。

从这个顺序，可以直接推出几条常考的规则：

  • WHERE 里不能用 SELECT 的别名。WHERE 是第 3 步，SELECT 是第 6 步，执行 WHERE 时别名还不存在。SELECT name, price * 0.8 AS sale FROM products WHERE sale < 100 在 MySQL 里报错 Unknown column 'sale' in 'where clause'。改成 WHERE price * 0.8 < 100，结果是鼠标 79.2、U盘 39.2。（SQLite 作为自己的扩展允许这样写，不报错；考题按标准答。）
  • ORDER BY 里可以用别名：它在 SELECT 之后。上面的 ORDER BY total 就是这样。
  • WHERE 里不能用聚合函数，HAVING 里可以：WHERE 在分组之前。
  • HAVING 在 SELECT 之前，按标准也不能用别名，所以上面写的是 HAVING SUM(o.quantity * p.price) > 200。MySQL 和 SQLite 都放宽了，允许写 HAVING total > 200，MySQL 甚至允许 GROUP BY 里用别名，这些都是方言扩展。
  • LIMIT 在 ORDER BY 之后：「取最贵的 3 个」是先排序再截取；如果不写 ORDER BY，LIMIT 取到的是哪几行没有保证。

这是逻辑顺序，规定了结果应该是什么。DBMS 实际执行时可以换一种更快的做法（比如利用第 8 课讲的索引直接找到 11 月的订单），只要结果和按这个顺序算出来的一样。

9. 动手玩：一条 SELECT 的执行过程

10. 子查询：IN 与 EXISTS

子查询：写在另一条 SQL 里面、用括号括起来的 SELECT。第 4 节说过，查询的结果集本身也是一张表，所以它可以出现在需要「一个值」或「一列值」或「一张表」的地方。

返回一个值的子查询（标量子查询）：「比平均价贵的商品」。

SELECT name, price FROM products
WHERE price > (SELECT AVG(price) FROM products);   -- 子查询先算出 329

结果只有显示器 999。注意不能直接写 WHERE price > AVG(price)：WHERE 里不能用聚合函数（第 8 节）。

返回一列值的子查询，配合 IN：「买过鼠标（2 号商品）的用户」。

SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE product_id = 2);

子查询返回 1、3、4（订单 2、4、6 的 user_id），外层查出张三、王五、赵六。

EXISTS (子查询)：子查询只要能查出至少一行就为真，查不出就为假，不关心查出的是什么（所以里面常写 SELECT 1）。
SELECT name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.product_id = 2);

这个子查询里用到了外层的 u.id，叫相关子查询：外层每处理一个用户，就把他的 id 带进去跑一次子查询。结果和上面的 IN 一样：张三、王五、赵六。

NOT IN 遇到 NULL 的坑：「不在北京以外某些城市的用户」这类题常这样设陷阱：

SELECT name FROM users WHERE city NOT IN (SELECT city FROM users WHERE id >= 5);

子查询返回 ('深圳', NULL)（孙七和周八的城市）。city NOT IN ('深圳', NULL) 等于 city <> '深圳' AND city <> NULL，后半个永远是 UNKNOWN，整个条件不可能为 TRUE，于是一行都查不出来。NOT EXISTS 没有这个问题：

SELECT u.name FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);   -- 周八

它和第 7 节的「LEFT JOIN … WHERE o.id IS NULL」是同一个意思的两种写法。

11. UNION 与 UNION ALL：把两个结果上下拼起来

JOIN 是把表左右拼（列变多），UNION 是把两个查询的结果上下拼（行变多）。要求两边的列数相同、对应列的类型兼容，结果的列名用第一个查询的。

SELECT city FROM users WHERE id <= 2          -- 北京、上海
UNION ALL
SELECT city FROM users WHERE id IN (2, 3);    -- 上海、北京

想给整个 UNION 的结果排序，ORDER BY 只能写在最后一个查询后面，它作用于拼好的整体。

13. 范式：为什么要把数据拆成三张表

第 2 节问过：为什么订单里只存 user_id，不直接写名字和城市？假设偷懒，只建一张大表：

反例：把一切塞进一张 orders_wide
order_iduser_nameuser_cityproduct_namepricequantity
1张三北京键盘1991
2张三北京鼠标992
4王五北京鼠标991

问题马上出来：张三的城市存了两遍，搬家时漏改一行就矛盾了（更新异常）；鼠标的价格存了好几遍（数据冗余）；周八没下过单，这张表里根本放不进他（插入异常）；删掉王五唯一的订单，王五这个人也跟着没了（删除异常）。范式就是避免这些问题的设计规则：

函数依赖：知道了 A 就能唯一确定 B，记作 A → B。例如 user_id → city：知道是几号用户，就知道他在哪个城市。

按 3NF 拆完，就是本课一直在用的三张表：用户的信息只在 users，商品的信息只在 products，orders 只记「谁、买了什么、几件、哪天」。代价是查询时要 JOIN 回来。实际中有时会故意冗余一两列（例如在订单里存下单时的价格，因为商品以后可能调价），这叫反范式设计，是为了查询快或保留历史，需要有明确理由。

自测

全部基于本课的三张表。

1. SELECT COUNT(*) FROM users u LEFT JOIN orders o ON o.user_id = u.id; 的结果是多少？换成 INNER JOIN 呢？ LEFT JOIN 是 9：8 笔订单各配上下单人，共 8 行，周八没有订单，补 1 行 NULL。INNER JOIN 是 8：只保留配对成功的行，周八消失。
2. 下列哪条 SQL 在 MySQL 里会报错？
A. SELECT city, COUNT(*) FROM users GROUP BY city;
B. SELECT name, price * 0.8 AS sale FROM products WHERE sale < 100;
C. SELECT name, price * 0.8 AS sale FROM products ORDER BY sale;
D. SELECT user_id FROM orders GROUP BY user_id HAVING COUNT(*) >= 2; B。WHERE 在执行顺序的第 3 步，SELECT 在第 6 步，执行 WHERE 时别名 sale 还不存在，报 Unknown column。C 的 ORDER BY 在 SELECT 之后，可以用别名。A、D 都是合法的分组写法（D 的结果是用户 1、2、4）。
3. SELECT name FROM users WHERE city <> '上海'; 返回几行？ 4 行：张三、王五、赵六、孙七。李四在上海被排除；周八的 city 是 NULL，NULL <> '上海' 是 UNKNOWN，WHERE 也不要他。6 − 1 − 1 = 4。
4. SELECT COUNT(*), COUNT(city), COUNT(DISTINCT city) FROM users; 的三个结果是？ 6、5、4。COUNT(*) 数行数；COUNT(city) 跳过周八的 NULL；COUNT(DISTINCT city) 是北京、上海、广州、深圳四种（两个北京只算一次，NULL 不算）。
5. SELECT name FROM products WHERE name LIKE '_盘' OR price BETWEEN 199 AND 299; 返回哪些商品？ 键盘、耳机、U盘。'_盘' 是「一个字 + 盘」，键盘、U盘都是两个字符，都匹配；BETWEEN 两头都包含，键盘 199、耳机 299 都在范围内。键盘两个条件都满足，也只出现一次（WHERE 是对每一行判断一次，不会让行变多）。
6. 关于 DELETE、TRUNCATE、DROP，下列说法错误的是？
A. DELETE 可以带 WHERE，TRUNCATE 不行
B. TRUNCATE 后表结构还在
C. TRUNCATE 和 DELETE 一样属于 DML，在 MySQL 里可以回滚
D. DROP 会把表结构和数据一起删掉 C。TRUNCATE 属于 DDL，MySQL 执行 DDL 时会自动提交，不能回滚；DELETE 才是 DML。另外 TRUNCATE 会把自增 id 重置。
7. 下面的查询返回几行？
SELECT u.city, COUNT(*) AS n FROM orders o JOIN users u ON o.user_id = u.id
GROUP BY u.city HAVING COUNT(*) >= 2;
 3 行：北京 3（张三的订单 1、2 加王五的订单 4）、上海 2（李四的订单 3、8）、广州 2（赵六的订单 5、6）。这里没有 WHERE，10 月的订单 5 也算在内，所以广州够 2 单；深圳只有 1 单，被 HAVING 去掉。注意别和第 8 节主查询混淆：那里 WHERE 先去掉了订单 5。
8. 订单表如果多一列 user_city（下单人的城市），它违反了第几范式？ 3NF。主键是 order_id，order_id → user_id → user_city，user_city 通过 user_id 间接依赖主键，是传递依赖。它仍然满足 2NF（主键只有一列，不存在「只依赖主键一部分」的情况）。后果是张三搬家时要改他的每一笔订单。
