第 9 课 · 事务与隔离级别

下单要改三张表，这三步必须要么全做、要么全不做，这就是事务。很多顾客同时下单时，事务之间会互相干扰；隔离级别规定了允许干扰到什么程度，数据库用锁和多版本（MVCC）来实现它。

开始前要会：第 7 课 SQL（表、行、主键，SELECT / UPDATE / INSERT，网店的 users / products / orders 三张表）、第 8 课 索引（B+ 树索引、主键索引，数据按页存在磁盘上）、第 3 课 并发、锁与死锁（竞态条件、互斥锁、死锁的四个必要条件）。

前两课讲了网店的数据怎么存、怎么查得快。这一课看「写」：顾客点下单按钮，网店程序要在数据库里连着改好几处；同一时刻还有别的顾客在买同一件商品。怎样保证数据不出错？整课都用同一件商品：商品 42（保温杯），stock = 10，price = 99，以及买它的用户 1，余额 300。

本课的路线：一次下单就是一个事务 → ACID 四个性质 → 原子性和持久性靠日志 → 并发事务的四种问题 → 隔离级别 → 锁 → MVCC → 间隙锁与幻读 → 数据库里的死锁 → 动手玩 → 用代码试试 → 九课串起来 → 题单怎么考。

1. 一次下单，就是一个事务

先给第 7 课的 users 表加一列余额（单位：元），用户 1 的余额是 300：

ALTER TABLE users ADD COLUMN balance DECIMAL(10, 2) NOT NULL DEFAULT 0;
UPDATE users SET balance = 300 WHERE id = 1;

用户 1 买 1 个商品 42，网店程序要执行三条语句：

UPDATE products SET stock = stock - 1 WHERE id = 42;                   -- ① 扣库存：10 → 9
INSERT INTO orders (user_id, product_id, quantity) VALUES (1, 42, 1);  -- ② 写订单
UPDATE users SET balance = balance - 99 WHERE id = 1;                  -- ③ 扣余额：300 → 201

如果执行完 ① ② 时服务器断电，或者 ③ 发现余额不够，就会留下「库存少了、订单有了、钱没扣」的烂摊子。我们要的是：三条语句当成一个整体。

事务（transaction）：数据库里一组操作的整体，这组操作要么全部生效，要么全部不生效。

用三条命令告诉数据库事务从哪开始、到哪结束：

  • BEGIN（或 START TRANSACTION）：开始一个事务。
  • COMMIT：提交，事务里的修改全部正式生效。
  • ROLLBACK：回滚，把事务里已经做的修改全部撤销，就像什么都没发生过。

如果不写 BEGIN，MySQL 默认开着自动提交（autocommit）：每条语句自己就是一个事务，执行完马上提交。所以要把几条语句绑在一起，必须显式写 BEGIN。

2. 事务的四个性质：ACID

说一个数据库「支持事务」，指的是它保证下面四件事，取英文首字母合称 ACID：

原子性（Atomicity）：事务里的操作要么全做，要么全不做，不会只做一半。「原子」就是「不可分割」，和第 3 课的原子操作是同一个意思。
一致性（Consistency）：事务执行前后，数据都满足业务规则。对网店来说：库存不为负，每卖出一件，库存少 1、多一条订单、余额少 99，三者对得上。
隔离性（Isolation）：多个事务同时执行时，互相不干扰，每个事务感觉不到别人正在改数据（干扰到什么程度算可以接受，由第 5 节的隔离级别决定）。
持久性（Durability）：事务一旦提交，修改就永久保存，之后哪怕断电、宕机也不会丢。

考试常问「哪个性质靠什么实现」：

性质靠什么在哪一节
原子性undo log（回滚日志）：记下修改前的旧值，回滚时照着改回去3
持久性redo log（重做日志）：提交时先把修改记到磁盘上的日志里3
隔离性锁 + MVCC（多版本并发控制）6、7
一致性是目的，由上面三个加上约束（第 7 课的 NOT NULL、外键等）共同保证

下面说到具体实现时，都以 MySQL 默认的存储引擎 InnoDB 为准（第 8 课提过它）。

3. 原子性和持久性：靠两种日志

第 8 课讲过：数据按页存在磁盘上，读写以页为单位，而磁盘比内存慢得多。所以 InnoDB 不会每改一行就去写磁盘，而是先在内存里改：

缓冲池（buffer pool）：InnoDB 在内存里开的一大块区域，缓存最近用过的数据页。读写数据都先在这里进行，改过的页以后再找时机写回磁盘。

这带来两个问题。① 事务改到一半要回滚，旧值去哪找？② 事务已经提交了，但改过的页还在内存里没写回磁盘，这时断电，修改就丢了，持久性怎么保证？InnoDB 用两种日志（按顺序记下「做了什么」的文件）来解决：

undo log（回滚日志）：每次修改一行之前，先记下这一行的旧值。回滚时照着 undo log 把数据改回去，这保证了原子性。（第 7 节会看到，它还被用来做 MVCC。）
redo log（重做日志）：每次修改，都记一笔「哪一页的哪个位置改成了什么」。事务提交时，必须先把这些记录写到磁盘上的 redo log 文件里，才算提交成功。断电重启后，按 redo log 把没来得及写回的修改重做一遍，这保证了持久性。

为什么不在提交时直接把数据页写回磁盘？一个事务改的几行可能分散在好几个页上，要在磁盘上跳来跳去写好几页（随机写）；而 redo log 是在文件末尾一条接一条地追加（顺序写），又小又快。这种「先写日志、再写数据」的做法叫预写日志（WAL，Write-Ahead Logging）。

4. 事务同时执行，会出什么问题

网店同一时刻有很多顾客，每个顾客的请求由服务器上的一个线程处理，每个线程开自己的事务。这些事务并发执行（第 1 课：一段时间内都在推进，操作互相交错）。第 3 课讲过线程交错会产生竞态条件：两个线程同时卖最后一件商品，结果出错。事务交错也一样，只是出问题的地方从内存变量换成了数据库里的行。

丢失修改：两个人同时卖，只扣了一次

A、B 两个顾客各买 1 个商品 42。网店程序的写法是「先读出库存，在程序里减 1，再写回去」：

丢失修改（lost update）：两个事务读了同一个数据，又先后修改它，后提交的把先提交的修改覆盖了。

这和第 3 课的竞态一模一样：「读、减、写」三步被另一个人插了进来。

脏读：读到了别人没提交的数据

B 扣了库存，但还没提交；这时 A 去读库存。如果 A 能看见 B 没提交的修改：

脏读（dirty read）：一个事务读到了另一个事务还没提交的修改。对方一旦回滚，读到的就是从未真正存在过的「脏数据」。

不可重复读：同一行，两次读的不一样

这次 B 正常提交了。A 在一个事务里先后读了两次商品 42 的价格（比如先展示给顾客，再算订单金额），中间 B 把价格从 99 改成 109 并提交：

不可重复读（non-repeatable read）：一个事务里两次读同一行，中间被别的事务修改（或删除）并提交，两次读到的值不一样。

幻读：同样的条件，多出了几行

A 按条件查一批行：「价格不超过 100 的商品」。假设店里符合条件的只有商品 42。这时 B 上架了一件新商品 43（price = 89）并提交：

幻读（phantom read）：一个事务里两次用同一个条件查询，中间别的事务插入了满足条件的新行并提交，第二次查到的行数变多了。

不可重复读和幻读很容易混：不可重复读盯的是同一行的值变了（UPDATE、DELETE 引起），幻读盯的是行的集合变了（INSERT 引起）。分开说，是因为防它们的办法不同：防不可重复读只要锁住读过的那几行，可新行在读的时候还不存在，锁不到它，要另想办法（第 8 节）。

5. 隔离级别：允许干扰到什么程度

最彻底的隔离是让事务一个接一个地执行，但网店就只能同时服务一个顾客了。隔离越严，事务之间要等待的越多，能同时处理的请求越少。所以 SQL 标准定义了四个隔离级别，让使用者在「正确」和「快」之间选：

隔离级别脏读不可重复读幻读
读未提交（READ UNCOMMITTED）会会会
读已提交（READ COMMITTED）不会会会
可重复读（REPEATABLE READ）不会不会会（标准的规定）
串行化（SERIALIZABLE）不会不会不会
  • 从上往下，每一级都比上一级多防一种问题。名字就是提示：读已提交只读已提交的数据，所以没有脏读；可重复读保证同一行重复读结果一样。
  • 串行化：并发执行的结果，和这些事务按某种顺序一个接一个执行的结果一样（这种性质叫可串行化）。最安全，也最慢。
  • 默认级别：MySQL InnoDB 默认可重复读；Oracle、PostgreSQL、SQL Server 默认读已提交。
  • InnoDB 的可重复读比标准更严：普通 SELECT 也看不到幻行（第 7、8 节讲原因）。考试如果问「标准规定可重复读能不能防幻读」，答「不能」。
  • 丢失修改不在表里。如果 B 在 A 没提交时直接改 A 改过的行（叫「脏写」），任何级别都不允许：UPDATE 总要加锁（第 6 节），B 会等 A 结束。但第 4 节那种「先读、在程序里算、再写回」的丢失修改，在 InnoDB 的读未提交、读已提交、可重复读下都会发生，要靠第 6 节的办法防。

MySQL 里查看和设置隔离级别：

SELECT @@transaction_isolation;                          -- 查看，默认 REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 只改当前连接

6. 锁：数据库怎么让事务排队

第 3 课的互斥锁同一时刻只让一个线程进临界区。数据库把锁分得更细：读和读不冲突，没必要互相排队。

共享锁（S 锁，读锁）：事务要读一行时加。多个事务可以同时持有同一行的 S 锁。
排他锁（X 锁，写锁）：事务要改一行时加。一行上有了 X 锁，别的事务的 S 锁和 X 锁都加不上，只能等。

两个事务对同一行加锁时能不能同时持有，看这张兼容矩阵：

B 想加 ＼ A 已持有S 锁X 锁
S 锁兼容，不用等冲突，B 等待
X 锁冲突，B 等待冲突，B 等待

记法：只有「读 + 读」能共存，只要有一方要写就冲突。InnoDB 里：

  • UPDATE、DELETE、INSERT 会自动给改动的行加 X 锁，一直持有到事务提交或回滚才释放。这就是任何级别都不会脏写的原因。
  • 普通 SELECT 默认不加锁（第 7 节讲它怎么读）；只有在串行化级别下，普通 SELECT 才会自动加 S 锁。
  • 想在读的时候就加锁，要显式写：SELECT … FOR SHARE（加 S 锁，老写法是 LOCK IN SHARE MODE）、SELECT … FOR UPDATE（加 X 锁）。

锁的粒度：锁住一整张表的叫表锁，开销小，但同一时刻只有一个事务能改这张表；只锁住几行的叫行锁，并发度高，但要管理的锁多。InnoDB 支持行锁，而且行锁是加在索引上的：WHERE id = 42 走主键索引（第 8 课），只锁商品 42 这一行；如果 WHERE 里的列没有索引，就只能全表扫描，扫过的每一行都被锁上，效果和锁表差不多。MyISAM 引擎只有表锁，也不支持事务。

封锁协议：锁加多久，决定防住什么

数据库教材里有一套「三级封锁协议」，规定 S 锁和 X 锁什么时候加、什么时候放。它和隔离级别是同一件事的两种说法，笔试常考：

协议规定防住了
一级改数据前加 X 锁，事务结束才放丢失修改
二级一级 + 读数据前加 S 锁，读完马上放丢失修改、脏读
三级一级 + 读数据前加 S 锁，事务结束才放丢失修改、脏读、不可重复读

为什么二级防不了不可重复读？A 读完 price 就放了 S 锁，B 就能加 X 锁改价、提交，A 再读时价格已经变了。三级把 S 锁一直留到 A 结束，B 只能等。

注意：教材里一级封锁协议的「改数据」包括「为了修改而读」，即 A 在读库存之前就加 X 锁，所以能防丢失修改。这正是下面的悲观锁。

和它相关的还有两段锁协议（2PL）：每个事务分两个阶段，先只加锁不放锁（扩展阶段），一旦开始放锁就不能再加锁（收缩阶段）。所有事务都遵守两段锁协议，并发执行的结果就是可串行化的。它是可串行化的充分条件，不是必要条件；而且它不能防止死锁（第 9 节）。

悲观锁和乐观锁：怎么防丢失修改

回到第 4 节两个顾客同时买的例子，有三种改法。第一种最简单：不在程序里算，让数据库算：

UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock > 0;

UPDATE 先给这一行加 X 锁，再读出最新的 stock 减 1，读和写之间没人插得进来。AND stock > 0 保证库存不会被扣成负数：库存为 0 时这条语句改了 0 行，程序看到「改了 0 行」就告诉顾客卖完了。

如果非要先读出来在程序里处理（比如要根据库存做复杂判断），就用下面两种锁：

悲观锁：假定一定会有人来抢，读的时候就加锁。用 SELECT … FOR UPDATE 读库存并加 X 锁，别的事务想读它来改，只能等。
乐观锁：假定很少有人来抢，读的时候不加锁，写的时候核对一下「这期间有没有人改过」。通常给表加一列版本号 version，每改一次加 1。它其实不是数据库里的锁，而是程序的写法。
-- 悲观锁
BEGIN;
SELECT stock FROM products WHERE id = 42 FOR UPDATE;   -- 读到 10，同时加 X 锁
UPDATE products SET stock = 9 WHERE id = 42;
COMMIT;                                                -- 释放锁，等着的 B 才能读，读到 9

-- 乐观锁：products 多一列 version，开始时是 1
SELECT stock, version FROM products WHERE id = 42;     -- 读到 (10, 1)
UPDATE products SET stock = 9, version = 2
 WHERE id = 42 AND version = 1;                        -- 改了 1 行：成功；改了 0 行：有人先改了，重读重试

7. MVCC：读的时候不加锁，也不读脏数据

如果只靠锁实现隔离，一个顾客在改商品 42 的库存（持有 X 锁），其他所有想看商品 42 页面的人都得等它提交，太慢了。InnoDB 的办法是：一行数据保留好几个版本，改的人生成新版本，读的人去读一个合适的旧版本，读写互不阻塞。这叫多版本并发控制（MVCC，Multi-Version Concurrency Control）。它由三样东西组成：

隐藏列：InnoDB 给每一行偷偷加了两列。trx_id：最后改这一行的事务的编号（每个事务开始时领一个递增的编号）。roll_pointer：指向这一行上一个版本的指针，上一个版本就存在 undo log 里（第 3 节）。
版本链：顺着 roll_pointer 一路往回，把同一行从新到旧的所有版本串起来的链表。
读视图（read view）：事务做普通 SELECT 时拍的一张「快照」，记下此刻还有哪些事务没提交。读一行时，从版本链最新的版本往回找，跳过读视图建立时还没提交的事务写的版本，返回第一个可见的版本（自己改的版本总是可见）。

四个隔离级别在 InnoDB 里分别是这样实现的：

级别普通 SELECT 怎么读
读未提交不用读视图，直接读版本链上最新的版本，哪怕还没提交，所以有脏读
读已提交每条 SELECT 新建一个读视图：总能看到「此刻」已提交的数据，所以没有脏读，但有不可重复读
可重复读事务里第一条 SELECT 建读视图，之后一直用它：整个事务看到的都是同一张快照
串行化不用快照，普通 SELECT 自动加 S 锁，靠锁让冲突的事务排队

快照读和当前读

到这里要分清 InnoDB 里两种「读」：

快照读：普通的 SELECT。通过读视图读版本链上的某个版本，不加锁。
当前读：SELECT … FOR UPDATE、SELECT … FOR SHARE，以及 UPDATE、DELETE、INSERT 内部的读。读的是最新的已提交版本，并且给读到的行加锁。

当前读不看读视图。比如在可重复读下，A 先快照读到 stock = 10，这时 B 卖出一件并提交（stock = 9）。A 再执行 UPDATE products SET stock = stock - 1 WHERE id = 42，UPDATE 是当前读，读到的是最新的 9，写成 8，结果正确。所以第 6 节说「让数据库去算」能防丢失修改；而「先快照读出 10、程序里算出 9、再写 9」就会丢失修改。

8. 幻读和间隙锁

回到第 4 节的幻读场景。在 InnoDB 的可重复读下：

  • 如果 A 用的是快照读，第二次查询沿用第一次的读视图，B 插入的商品 43 是读视图建立之后才提交的，看不见，所以没有幻读。
  • 如果 A 用的是当前读（例如 SELECT id FROM products WHERE price <= 100 FOR UPDATE，要读到最新数据并锁住它们），读视图帮不上忙。只锁住已有的行 42 也不够，因为 43 根本还不存在。

InnoDB 的办法是连同行与行之间的「空隙」一起锁上。设 price 列上有索引（第 8 课的二级索引），索引里的值是排好序的，相邻两个值之间就是一个间隙：

间隙锁（gap lock）：锁住索引里两个相邻值之间的区间，不让别的事务往这个区间里插入新行。它只防插入，不锁已有的行。
临键锁（next-key lock）：一行的行锁（叫记录锁）加上它前面那个间隙的间隙锁。InnoDB 在可重复读下做当前读时，默认加的就是临键锁。

两点补充：

  • 如果 price 列没有索引，InnoDB 只能全表扫描，会把每一行和每个间隙都锁上，相当于锁表。这又是一个「WHERE 里的列要有索引」的理由。
  • InnoDB 的可重复读并没有完全消灭幻读：A 先快照读（只看到 42），B 插入 43 并提交，A 再执行一条当前读的 UPDATE 碰到了 43，那么 A 之后的快照读也会看到 43（自己改过的版本总是可见）。真要绝对没有，用串行化。

9. 数据库里的死锁

有了行锁，第 3 课的死锁也会出现在数据库里。网店有两种事务都要改商品 42 和用户 1 这两行：

  • 事务 A（下单）：先扣商品 42 的库存，再扣用户 1 的余额。
  • 事务 B（退货）：先给用户 1 退 99 元，再把商品 42 的库存加回去。
A：UPDATE products SET stock = stock - 1 WHERE id = 42;    -- A 锁住商品 42
B：UPDATE users SET balance = balance + 99 WHERE id = 1;   -- B 锁住用户 1
A：UPDATE users SET balance = balance - 99 WHERE id = 1;   -- 等 B 放用户 1 的锁
B：UPDATE products SET stock = stock + 1 WHERE id = 42;    -- 等 A 放商品 42 的锁：死锁

对照第 3 课的四个必要条件：X 锁一次只能给一个事务（互斥）；A 拿着商品 42 又去要用户 1（占有并等待）；锁只能等持有者提交或回滚才释放，别人抢不走（不可抢占）；A 等 B、B 等 A（循环等待）。四条全满足。

InnoDB 怎么处理：

  • 死锁检测：每当一个事务要等锁，InnoDB 就检查「谁在等谁」有没有成环（这张图叫等待图）。一旦成环，就挑一个事务回滚（通常是改动行数少、回滚代价小的那个），报错 Deadlock found when trying to get lock，它的锁随之释放，另一个事务就能继续。被回滚的事务由程序重试。
  • 锁等待超时：等锁超过 innodb_lock_wait_timeout（默认 50 秒）就放弃这条语句并报错。

怎么预防：还是第 3 课的「破坏循环等待」，所有事务按同一个顺序加锁。比如规定一律先改 products 再改 users，B 改成先加库存再退钱，就不会成环。另外，事务要尽量短（锁持有的时间短），WHERE 条件要走索引（锁的行少）。

10. 动手玩：两个事务的时间线

先在上面一排选一个隔离级别（默认是 MySQL 的「可重复读」），再选一个场景。动画每一步执行一条语句：左列是事务 A 执行过的语句，右列是事务 B 的，同一行编号表示同一时刻。中间是数据库：商品 42 的版本链（左边最新；虚线橙框是还没提交的版本，绿色外圈是 A 刚才读到的那个版本）、当前的锁，以及 A 最近一次 SELECT 读到的值。播完后最下面给出结论。

建议这样玩：

  1. 「读未提交」+「脏读」：A 第二次读到 9，B 回滚后又变回 10。
  2. 换成「读已提交」再点「脏读」：A 跳过了 B 没提交的版本。接着点「不可重复读」：A 两次读到 99 和 109。
  3. 换成「可重复读」点「不可重复读」：A 沿用第一次的读视图，两次都是 99。再点「幻读」：快照读看不到商品 43。
  4. 换成「串行化」点任一场景：普通 SELECT 也加 S 锁，B 的冲突语句只能等待锁。点「丢失修改」还能看到第 9 节的死锁。
  5. 任何级别下点「丢失修改」，对比一下「先读、在程序里算、再写回」有多危险。

动画里的规则就是第 6～8 节讲的：UPDATE / INSERT 加 X 锁直到事务结束；读已提交每条 SELECT 新建读视图，可重复读只在第一条 SELECT 时建；串行化下普通 SELECT 加 S 锁（范围查询连间隙一起锁）。

11. 用代码试一试

仓库里的 examples/transaction_in_practice.py 只用 Python 标准库里的 sqlite3（SQLite 是一个嵌在程序里的小数据库，不用装服务器），演示两件事：

  1. 原子性：用户 1 下单成功，stock 10 → 9、余额 300 → 201；余额只有 50 的用户 2 下单，第 ③ 步扣余额失败，ROLLBACK 之后库存还是 9、订单还是 1 条，第 ① 步扣的库存被撤销了。
  2. 防超卖：商品 42 只剩 1 件，两个连接同时来买。「先读、在程序里减 1、再写回」两边都卖出去了（丢失修改，实际卖了 2 件）；换成 UPDATE … SET stock = stock - 1 WHERE id = ? AND stock > 0，第二个人改了 0 行，知道卖完了；用乐观锁 version 列，第二个人的 UPDATE 也是改了 0 行，重读后发现库存为 0。
uv run examples/transaction_in_practice.py

脚本里每个结论都用 assert 检查，跑完退出码为 0。注意：SQLite 的隔离模型和 MySQL 不一样。它没有行锁，写的时候锁住整个数据库文件，同一时刻只允许一个事务写；也不能像 MySQL 那样把隔离级别设成读已提交、可重复读。所以四个隔离级别的差别只能在上面的动画里看，脚本只演示原子性和防超卖这两种和数据库种类无关的做法。

12. 九课串起来：顾客点下单按钮之后

这是本系列最后一课。回到第一课开头那家网店，把一次下单从头到尾走一遍，每一步都是前面某一课讲过的东西：

  1. 浏览器：顾客点「下单」，浏览器要把请求发给网店的域名（第 6 课：URL 的结构）。
  2. DNS：先把域名换成服务器的 IP 地址；数据包按 IP 逐跳转发到服务器（第 4 课）。
  3. TCP：浏览器和服务器的 443 端口三次握手，建立可靠的连接（第 5 课）。
  4. HTTP：在 TLS 加密的连接上发一个 POST 请求，正文里是「用户 1 买 1 个商品 42」（第 6 课）。
  5. 进程和线程：服务器上的 shop-server 进程收到请求，交给一个线程处理；调度器让它轮流用 CPU（第 1 课）；它的代码和数据都在虚拟内存的页里（第 2 课）；许多线程同时处理不同顾客，共享的数据要靠锁保护（第 3 课）。
  6. SQL：线程向数据库发出扣库存、写订单、扣余额三条语句（第 7 课）。
  7. 索引：WHERE id = 42 顺着主键的 B+ 树三四次磁盘读就找到了那一行，而且行锁只锁这一行（第 8 课）。
  8. 事务：三条语句包在 BEGIN … COMMIT 里，undo log 保证出错能回滚，redo log 保证提交后不丢（本课第 1～3 节）。
  9. 锁与 MVCC：同时买商品 42 的其他顾客，在 X 锁上排队；只是来看商品页的顾客，读快照，不用等（本课第 6～9 节）。
  10. 返回响应：提交成功，服务器回一个 HTTP 响应（例如 201 Created），浏览器显示「下单成功」（第 6 课）。

自测

1. 下单事务执行完扣库存、写订单后，扣余额失败，程序执行了 ROLLBACK。数据库靠什么把库存改回 10？这体现了 ACID 的哪一条？ 靠 undo log。扣库存之前，InnoDB 先在 undo log 里记下「商品 42 的 stock 原来是 10」，回滚时照着改回去；写订单那一步也同样被撤销。这体现的是原子性：三步要么全做，要么全不做。
2. 事务提交成功后数据库马上断电，改过的数据页还没写回磁盘。重启后修改还在吗？靠的是什么？ 在。提交时 redo log 已经先写到了磁盘上（预写日志 WAL），重启后按 redo log 把修改重做一遍。这体现的是持久性。
3. 事务 A 读到了事务 B 修改后还没提交的数据，B 随后回滚。这是什么问题？最低要用哪个隔离级别才能避免？ 脏读。最低用读已提交：它只让事务读已经提交的数据。读未提交是唯一会出现脏读的级别。
4. 下列说法正确的是：A. MySQL InnoDB 默认隔离级别是读已提交　B. Oracle 默认隔离级别是可重复读　C. 按 SQL 标准，可重复读能防止不可重复读，但不能防止幻读　D. 串行化仍可能出现脏读 C。A 错，InnoDB 默认是可重复读；B 错，Oracle 默认读已提交；D 错，串行化四种问题都不会出现。（InnoDB 的可重复读借助 MVCC 和间隙锁，实际上能防住大部分幻读，但题目问「标准」时答不能。）
5. 事务 A 对商品 42 持有 S 锁。事务 B 想对同一行加 S 锁、加 X 锁，分别会怎样？ 加 S 锁：兼容，立即成功，两个事务可以同时读。加 X 锁：冲突，B 要等 A 提交或回滚释放 S 锁之后才能加上。记法：只有「读 + 读」能共存。
6. 商品 42 的 stock = 10、version = 3。A、B 都读到 (10, 3)，然后各自执行 UPDATE products SET stock = stock - 1, version = version + 1 WHERE id = 42 AND version = 3，A 先执行。B 的语句改了几行？B 重读后重试成功，最终 stock 和 version 各是多少？ A 执行后变成 (9, 4)。B 的 WHERE version = 3 已经匹配不上，改了 0 行，程序据此知道有人先改过。B 重读到 (9, 4)，用 WHERE version = 4 再执行一次，成功，变成 stock = 8、version = 5。两次修改都生效了，没有丢失修改。
7. 三级封锁协议中，能防止不可重复读的是哪一级？为什么二级不行？ 三级。二级规定读之前加 S 锁、读完马上释放，A 两次读之间 B 就能加 X 锁改数据并提交，A 第二次读到的就不一样了。三级把 S 锁一直留到 A 事务结束，B 想改只能等，所以 A 两次读的结果相同。
8. 事务 A 先锁商品 42 再锁用户 1，事务 B 先锁用户 1 再锁商品 42，结果死锁了。InnoDB 会怎么处理？怎样改写程序才能避免？ InnoDB 的死锁检测发现等待图成环，回滚其中一个事务（通常是回滚代价小的那个）并报 Deadlock found 错误，另一个事务得以继续；被回滚的那个由程序重试。避免的办法是破坏「循环等待」：规定所有事务按同一顺序加锁，例如一律先改 products 再改 users。
