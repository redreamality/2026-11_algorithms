第 8 课 · 索引与查询优化

表的数据存在磁盘上，按页读写，读一页很慢。索引是按某几列排好序、组织成 B+ 树的一份额外数据：查一行只要读 3～4 页，而不是把几十万页全读一遍。会不会用上索引，取决于 WHERE 条件写得对不对。

开始前要会：第 7 课的表、主键、SELECT / WHERE / ORDER BY 和网店的 users / products / orders 三张表；第 2 课的「页」，以及「磁盘比内存慢得多、读写以页为单位」。本课会用到「树」，第 3 节从头讲，不需要事先学过。

第 7 课的网店只有 8 笔订单。一年过去，网店做大了：orders 表长到了 3000 万行。顾客点开「我的订单」，网店程序发出 SELECT * FROM orders WHERE user_id = 7，要等好几秒；运营查「11 月的订单」也一样慢。SQL 没写错，结果也对，就是慢。这一课找出慢在哪里，以及怎么用索引让它快起来。为了下面的例子，本课给 orders 表加了一列 status（订单状态：unpaid 待付款、paid 已付款、shipped 已发货、refund 已退款），其余各列和第 7 课一样：id, user_id, product_id, quantity, created_at。

本课的路线：数据在磁盘上按页读 → 全表扫描为什么慢 → 索引是什么 → 先认识树，看哈希表和二叉搜索树为什么不合适 → B 树与 B+ 树 → 三层能存多少行 → 动画 1 → 聚簇索引、二级索引与回表 → 覆盖索引 → 联合索引与最左前缀 → 动画 2 → 索引失效 → 索引的代价 → EXPLAIN → 自增主键与页分裂 → InnoDB 与 MyISAM → 题单怎么考。

1. 数据在磁盘上，按页读写

第 2 课讲过：内存装不下的东西放在磁盘上，磁盘比内存慢得多，而且读写不是一个字节一个字节来，而是一次一整页。数据库也是这样存表的。

存储引擎：DBMS 里负责「把表存到磁盘上、再读出来」的那部分。MySQL 可以换不同的存储引擎，默认（5.5 起）是 InnoDB，本课以它为准。第 15 节和老引擎 MyISAM 对比。
页（数据页）：InnoDB 读写磁盘的最小单位，默认大小 16KB（是操作系统 4KB 页的 4 倍）。表里的行一行行地放在页里；要读某一行，就得把它所在的整页从磁盘读进内存。
缓冲池（Buffer Pool）：InnoDB 在内存里划出的一大块区域，存放最近读进来的页。要的页已经在缓冲池里，就不用再读磁盘。

算一下 3000 万行的 orders 表占多少页。一行订单（6 个列，加上 InnoDB 给每行附带的管理信息）约 160 字节，一页能放 16384 ÷ 160 ≈ 100 行，于是 3000 万 ÷ 100 = 30 万页，合 300000 × 16KB = 4 800 000 KB，约 4.6 GB。

全表扫描：把表的所有页逐页读一遍，对每一行检查 WHERE 条件。没有可用的索引时，DBMS 只能这样做。

第 7 课的 WHERE user_id = 7 就是这样执行的：表是按 id 的顺序存的，7 号用户的那几笔订单散落在 30 万页里的某几页，不知道在哪几页，只好 30 万页全读一遍、对 3000 万行逐个比较。找 5 行，读 4.6 GB，这就是慢的原因。

所以本课衡量快慢只看一件事：读了几页。

2. 索引是什么

一本 500 页的书，要找「死锁」在哪讲，没人从第 1 页翻起，而是翻到书末的「索引」：词条按拼音排好序，后面写着页码。数据库的索引是同一个思路。

索引：按表里某一列（或某几列）的值排好序的一份额外数据，每一项是「列的值 + 能找到那一行的位置」。例如在 user_id 上建的索引，每一项是 (user_id, 那一行的主键 id)。建法：CREATE INDEX idx_user_id ON orders(user_id);

为了能画出来，下面把 orders 表缩小成 27 行、9 页（一页 3 行），本课的图和动画都用这张缩小版。其中 7 号用户有 5 笔订单：id 2、7、8、15、18。

有了索引，DBMS 就有了两种做法：全表扫描，或者先查索引再按 id 取行。选哪种由它自己决定：

查询优化器：DBMS 里给每条 SQL 挑执行办法的部分。它估算每种办法大约要读多少页，挑最省的。第 7 课说 SQL「只说要什么，不说怎么找」，「怎么找」就是优化器定的。

剩下的问题是：「排好序的一份数据」在磁盘上具体怎么组织？如果只是一个按 user_id 排序的长数组，查找可以用二分（每次和中间那项比，砍掉一半），但网店每秒都在下新订单，往有序数组中间插一项，后面几千万项都得往后挪，太慢。我们要的结构得同时满足：有序、查得快、插得快、读的页少。答案是一种树。

3. 先认识树；为什么不用哈希表和二叉搜索树

树的几个名词

树：由节点和连接节点的边组成的结构，像一棵倒过来的树。最上面的节点叫根；一个节点往下连着的节点叫它的子节点；没有子节点的节点叫叶子。从根走到叶子要经过几层节点，叫树的高度（本课按层数算，只有一个根的树高度为 1）。
二叉搜索树（BST）：每个节点存一个键、最多两个子节点，并且左边子树的键都比它小，右边子树的键都比它大。查找时从根开始，比它小就往左、比它大就往右，每层只比一次。平衡的二叉搜索树（各条从根到叶子的路径长度差不多）存 n 个键，高度约为 log2n。想深入看：算法课 · 二叉搜索树、算法课 · 平衡树。

树放在磁盘上时，一个节点就存在一页里，从父节点走到子节点 = 多读一页。所以对数据库来说，树的高度就是查一行要读的页数。

为什么不用哈希表

哈希表：用一个哈希函数把键算成一个桶号，直接到那个桶里去找。例如 桶号 = user_id ÷ 4 的余数。等值查找只算一次，非常快。

网店到处是范围查询：「11 月的订单」「金额大于 100 的订单」「最近 10 笔订单」。所以 InnoDB 默认的索引不用哈希表。（MySQL 的 MEMORY 引擎可以显式建哈希索引；InnoDB 内部有一个「自适应哈希索引」，是它自动给热点数据加的辅助结构，不能手动建。）

为什么不用二叉搜索树

二叉搜索树有序，能做范围查询。问题出在太高。每个节点只有一个键、两个分叉，3000 万行要多少层？224 ≈ 1678 万，225 ≈ 3355 万，所以即使完全平衡也要约 25 层，查一行读 25 页。机械硬盘随机读一页约 10 毫秒，25 页就是 0.25 秒，一个页面查几次就要一两秒。

还有一个问题：二叉搜索树按插入顺序长，订单 id 是一个比一个大地插入的，不做平衡就会长成一条向右的长链，高度等于行数。平衡树能解决这一点，但解决不了「每页只放一个键」的浪费。

4. B 树与 B+ 树：让每个节点多分叉

多路搜索树：二叉搜索树的推广。一个节点里存好几个排好序的键，k 个键把取值切成 k + 1 段，每段对应一个子节点。一个节点最多有几个子节点，叫这棵树的阶；实际有几个子节点叫它的扇出。扇出越大，树越矮。

例如一个节点里存键 10、19，就把 id 切成三段：小于 10、10～18、大于等于 19，分别走第 1、2、3 个指针。查找时在节点里比较几次（这是在内存里比，很快），然后往下读一页。

B 树：一种保持平衡的多路搜索树：所有叶子都在同一层；插入和删除时自动拆分、合并节点，保证不会长歪。每个节点里既存键，也存这个键对应的整行数据。
B+ 树：B 树的变种，InnoDB 的索引用的就是它。和 B 树有三点不同：① 非叶子节点只存键和指针，不存数据；② 所有数据都在叶子里，非叶子里的键在叶子里会再出现一次；③ 叶子之间用链表按顺序串起来，每个叶子都记着右边（InnoDB 里左右都记）的邻居在哪一页。

这三点各自解决一个问题：

B+ 树的设计带来的好处
非叶子只存键和指针一页能放上千个键，扇出大 → 树矮 → 读页少（下一节算具体数）
数据只在叶子任何查找都走到叶子，读页次数稳定，等于树的高度
叶子用链表串起来范围查询：找到起点所在的叶子后，顺着链表往右读，不用回到上层；按索引顺序 ORDER BY 也是这样免掉排序

5. 三层 B+ 树能存多少行

这是常考的估算题。按 InnoDB 的典型配置一步步算：

  1. 非叶子节点里的一项多大：主键用 BIGINT，占 8 字节；指向子页的指针占 6 字节。一项 = 8 + 6 = 14 字节。
  2. 一个非叶子节点能有多少个子节点：一页 16KB = 16 × 1024 = 16384 字节，16384 ÷ 14 ≈ 1170.3，取 1170。也就是扇出约为 1170。
  3. 一个叶子放多少行：叶子存整行。教材通常假设一行 1KB，一页放 16384 ÷ 1024 = 16 行。
  4. 每层有多少页：第 1 层（根）1 页；第 2 层 1170 页；第 3 层（叶子）1170 × 1170 = 1 368 900 页。
  5. 总行数：1 368 900 × 16 = 21 902 400 行，约 2000 万行。

换成我们的 orders 表：一行约 160 字节，叶子每页约 100 行，三层能存 1170 × 1170 × 100 = 136 890 000 行，约 1.4 亿。3000 万行的 orders 三层就够：按主键查任意一行，读 3 页。对比一下：两层只能存 1170 × 100 = 117 000 行；四层能存一千多亿行，网店用不到。

还有一个更好的消息：前两层一共只有 1 + 1170 = 1171 页，1171 × 16KB ≈ 18.3 MB，常年待在缓冲池里。所以实际上查一行往往只有读叶子那 1 次是真的读磁盘。

注意这是估算：页里还有页头、页尾、空闲空间等开销，真实数字会小一些。考题问「三层 B+ 树大约能存多少行」，答「约 2000 万（千万级）」即可，要会写上面五步。

6. 动手玩 1：B+ 树查找 vs 全表扫描

下面是第 2 节那张 27 行的缩小版 orders 表，按主键 id 建成的三层 B+ 树：每个方框是一页，叶子一页放 3 行。根的键 10、19 把 id 分成「小于 10、10～18、大于等于 19」三段；第 2 层同理。

  • 输入 14，点用索引查找：根 → 第 2 层 → 叶子，读 3 页。换成 1、27、或者不存在的 30，都是 3 页。
  • 点全表扫描：9 个叶子页全读一遍，读 9 页。表越大，差距越大：30 万页的表，索引查找还是 3 页。
  • 起点 8、终点 20，点范围查询：先 3 页找到 8 所在的叶子，再沿链表往右读 4 页，一共 7 页，拿到 13 行。

7. 聚簇索引、二级索引与回表

上面的动画里，叶子里存的就是整行数据，这棵树本身就是表。InnoDB 正是这样存表的：

聚簇索引（也叫主键索引）：按主键建的 B+ 树，叶子里存整行数据。表的数据就按主键顺序存在这棵树的叶子里，「索引」和「数据」是一回事，所以一张表只能有一个聚簇索引。没定义主键时，InnoDB 拿第一个非空的 UNIQUE 列来当；还没有，就自己加一个隐藏的 6 字节行号。
二级索引（也叫辅助索引、非聚簇索引）：在其他列上建的 B+ 树，例如 idx_user_id。它按 user_id 排序，叶子里只存 (user_id, 主键 id)，不存整行。一张表可以有多个二级索引。
回表：通过二级索引找到主键 id 后，再拿着 id 去聚簇索引里从根往下查一次，取出整行。

所以 SELECT * FROM orders WHERE user_id = 7 的代价是：二级索引往下走 3 层 + 沿叶子读完 user_id = 7 的项，然后回表 5 次，每次在聚簇索引里走 3 层。比全表扫描的 30 万页少太多了。但回表的次数等于匹配的行数：如果条件匹配上百万行，回表一百万次反而比全表扫描还慢，这时优化器会放弃索引，直接全表扫描。

8. 覆盖索引：不回表

回表是因为二级索引里没有查询要的列。如果查询要的列，二级索引里全都有，就不用回表了。

覆盖索引：一条查询用到的所有列（SELECT 的列、WHERE 的列、ORDER BY 的列……）都包含在某个索引里，只读这个索引就能得到结果，不用回表。这时我们说「这个索引覆盖了这条查询」。注意：二级索引的叶子里本来就带着主键，所以主键列也算「索引里有」。

这也是为什么常说「别写 SELECT *」：只要真正需要的列，才有机会用上覆盖索引。「我的订单」列表页如果只显示状态和下单时间，下一节的联合索引 (user_id, status, created_at) 就能覆盖它。

9. 联合索引与最左前缀

联合索引（也叫组合索引、复合索引）：在多列上建的一个索引，例如 CREATE INDEX idx_u_s_c ON orders(user_id, status, created_at);。它的项先按 user_id 排序；user_id 相同的，再按 status 排序；前两列都相同的，再按 created_at 排序。就像字典先按第一个字母排，第一个字母相同再比第二个。

网店的「我的订单 → 已付款」页面要查 WHERE user_id = 7 AND status = 'paid'，按时间排序。这个联合索引正好为它而建。看看它的叶子里，项是怎么排的（还是那 12 项，叶子末尾附带主键 id）：

B+ 树能快速定位，靠的是「有序」。于是规则就出来了：

最左前缀匹配：联合索引只能从最左边的列开始，连续地用上若干列来定位。(a, b, c) 上的索引，能用来定位的组合是 a、(a, b)、(a, b, c)，这些叫索引的最左前缀。中间断了一列，后面的列就用不上；某一列用的是范围条件（>、<、BETWEEN、LIKE 'abc%'），这一列能用上，但它右边的列就用不上了。

逐个看网店的几个查询（「用上」指用来在 B+ 树里定位）：

WHERE 条件用上的列为什么
user_id = 7user_id最左一列，等值
user_id = 7 AND status = 'paid'user_id, statususer_id 相同的一段里 status 有序
status = 'paid' AND user_id = 7user_id, statusAND 两边可以交换，优化器会自己调整顺序。最左前缀看的是索引列的顺序，不是 WHERE 的书写顺序
user_id = 7 AND status = 'paid' AND created_at > '2026-11-01'三列全用上前两列等值，最后一列范围
status = 'paid'一列也用不上缺了最左列 user_id。status 在整个索引里是乱的
user_id = 7 AND created_at > '2026-11-01'只有 user_id跳过了 status，在 user_id = 7 那一段里 created_at 是乱的（看图：11-02 排在 11-05 后面）
user_id > 5 AND status = 'paid'只有 user_iduser_id 是范围，6、7、8、9 混在一起，这一大段里 status 是乱的

用不上来定位的条件并不是被忽略了：DBMS 在定位到的那一段里逐项检查它们，结果照样正确，只是要多看几项。MySQL 5.6 起还能在二级索引的项里先检查这些条件、不满足的就不回表（叫索引下推，EXPLAIN 的 Extra 显示 Using index condition），省掉一部分回表。

把这个规则反过来用，就是建联合索引的口诀：等值条件的列放前面，范围条件的列放最后；同样是等值，经常单独出现的列放最左（例如 user_id），这样一个 (user_id, status, created_at) 就能同时服务「某用户的全部订单」「某用户某状态的订单」两种查询，不必再单独建 idx_user_id。

11. 索引失效：建了索引却没用上

「索引失效」指的是：列上明明有索引，但 WHERE 写法让优化器没法用它来定位，只好全表扫描。原因几乎都是同一个：B+ 树是按列本身的值排序的，条件必须能直接拿列的值去比。常见的五种：

情况例子（orders 上有 idx_user_id、idx_u_s_c）为什么用不上 / 怎么改
对列做运算或套函数WHERE user_id + 1 = 8
WHERE MONTH(created_at) = 11		树按 user_id 排序，不按 user_id + 1 排序。把运算挪到另一边：user_id = 8 - 1；created_at >= '2026-11-01' AND created_at < '2026-12-01'
隐式类型转换假如手机号列 phone 是 VARCHAR：WHERE phone = 13800000000（没加引号）字符串和数字比较时，MySQL 把列的每个值转成数字再比，等于对列套了函数。写成 phone = '13800000000'。反过来，数字列和字符串比（user_id = '7'）转换的是常量，索引还能用
LIKE 以 % 开头WHERE name LIKE '%盘'（products.name 上有索引）不知道第一个字，就不知道从树的哪里开始找。LIKE 'U%' 可以用：它等于范围条件「以 U 开头」
OR 连了没索引的列WHERE user_id = 7 OR quantity = 3quantity = 3 的行只能靠全表扫描找；反正要扫一遍，索引就白用了。两边的列都有索引时，MySQL 可以分别查再合并（Extra 显示 Using union）
不满足最左前缀WHERE status = 'paid'（只有 idx_u_s_c）第 9 节：缺了最左列 user_id

还有一种不算「失效」但效果一样的：优化器估计用索引更慢。例如 WHERE status = 'paid' 假如单独有 status 的索引，但 3000 万行里有一半是 paid，用索引要回表 1500 万次，不如直接全表扫描。所以 !=、IS NOT NULL 这类匹配行很多的条件，经常也走全表扫描，取决于数据分布。

12. 索引的代价，哪些列适合建索引

索引不是越多越好。每个二级索引都是一棵独立的 B+ 树，代价有三项：

  • 占空间：idx_user_id 每项存 (user_id, id)，3000 万项也要几百 MB。
  • 拖慢写入：每 INSERT 一笔订单，除了聚簇索引，每个二级索引也要插入一项；UPDATE 了被索引的列、DELETE 一行，相关的索引都要跟着改。orders 上建 5 个索引，下单就要改 6 棵树。
  • 让优化器多费心：可选的索引多了，选错的可能也多了。
区分度（选择性）：一列里不同值的个数 ÷ 总行数，越接近 1 越好。orders 的主键 id 区分度是 1；user_id 有几十万种值，区分度高；status 只有 4 种值，区分度约 4 ÷ 3000 万，接近 0，按它单独查一次要命中几百万行。
适合建索引不适合建索引
经常出现在 WHERE、JOIN … ON、ORDER BY、GROUP BY 里的列（user_id、created_at）很少用来查询的列（quantity）
区分度高的列区分度低的列单独建（status、性别）；可以放在联合索引的中间
外键列（JOIN 要用，例如 orders.user_id）数据很少的小表（products 只有几千行，全表扫描也就几十页）
能顺便覆盖常用查询的联合索引频繁更新、又很少查询的列

13. EXPLAIN：看一条查询用没用上索引

执行计划：优化器为一条 SQL 选定的具体做法：先读哪张表、用哪个索引、大约读多少行。在 SQL 前面加 EXPLAIN，MySQL 就不执行它，而是把执行计划列出来。
EXPLAIN SELECT * FROM orders WHERE user_id = 7 AND status = 'paid';

结果是一张表，考题和日常排查主要看四列：

列含义重点
type访问方式，从好到差：const（按主键或唯一索引等值查，最多 1 行）> eq_ref（JOIN 时按对方主键查）> ref（普通索引等值查）> range（索引范围查）> index（把整个索引扫一遍）> ALL（全表扫描）出现 ALL 就要警惕；一般至少要到 range
key实际用的索引名，NULL 表示没用索引（possible_keys 是可能用的）上面这条显示 idx_u_s_c
rows优化器估计要检查多少行越少越好；和实际返回的行数差很多，说明索引不够准
Extra附加说明Using index = 覆盖索引，不回表；Using where = 取出行后还要再用 WHERE 过滤；Using index condition = 索引下推；Using filesort = 要额外排序，不能靠索引顺序

（另外 key_len 表示用上的索引列一共多少字节，可以据此推出联合索引用上了几列。）

本课的实战脚本 examples/index_in_practice.py（运行：uv run examples/index_in_practice.py）只用 Python 自带的 sqlite3，造一张 5 万行的 orders 表，用 SQLite 的 EXPLAIN QUERY PLAN 把本课的结论逐条验证一遍：没索引、建索引后、覆盖索引、对列做运算、OR、联合索引的每种 WHERE 条件。SQLite 的输出是一句话，和 MySQL EXPLAIN 的对应关系如下：

SQLite 的 EXPLAIN QUERY PLAN对应 MySQL EXPLAIN
SCAN orderstype = ALL，全表扫描
SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)type = const，key = PRIMARY（SQLite 的 INTEGER PRIMARY KEY 就是聚簇的主键）
SEARCH orders USING INDEX idx_user_id (user_id=?)type = ref，key = idx_user_id，会回表
SEARCH … USING INDEX idx_u_s_c (user_id>?)type = range
SEARCH … USING COVERING INDEX …Extra = Using index，覆盖索引
括号里的 (user_id=? AND status=?)用上了联合索引的哪几列（MySQL 要看 key_len 推算）

脚本的输出里，联合索引那几条正好印证了第 9 节的表：user_id = 7 AND created_at > … 括号里只有 (user_id=?)；user_id > 5 AND status = 'paid' 只有 (user_id>?)；status = 'paid' 直接变成 SCAN orders。

14. 为什么主键推荐自增：页分裂

聚簇索引的叶子按主键顺序存满整行，一页 16KB 装满就不能再塞了。新插入的行放在哪，取决于它的主键：

页分裂：新行按主键应该插进一个已经满了的页的中间时，InnoDB 只好申请一个新页，把原页的大约一半行挪过去，两页各半满，再把新行插进去，同时还要在父节点里加一项（父节点也满了就接着往上分裂）。

所以 InnoDB 的主键推荐用自增整数（BIGINT AUTO_INCREMENT）：

  • 插入总在末尾，几乎不发生页分裂，页都填得满满的；
  • 主键短（8 字节）：每个二级索引的叶子都要存一份主键，主键越短，二级索引越小。用 36 个字符的 UUID 当主键，每个二级索引都跟着变胖；
  • 非叶子节点里的键也短，扇出更大（第 5 节的 14 字节就是这么来的）。

同理，不要拿业务上会变的列（手机号、身份证号）当主键：主键一改，这一行在聚簇索引里要挪位置，所有二级索引里存的主键也都要跟着改。

15. InnoDB 与 MyISAM

MyISAM 是 MySQL 5.5 以前的默认存储引擎，现在已很少用，但常和 InnoDB 对比着考：

InnoDB（默认）MyISAM

锁行锁（只锁改动的行）表锁（改一行锁整张表）

崩溃后恢复能，靠日志（第 9 课）容易丢数据或损坏
COUNT(*) 不带 WHERE要扫描一个索引去数直接返回存好的总行数，很快

自测

1. MySQL InnoDB 的索引默认采用哪种数据结构？A. 哈希表　B. 二叉搜索树　C. B 树　D. B+ 树 D。B+ 树的非叶子只存键和指针，一页能装上千个键，三层就能存千万行，查一行只读 3 页；叶子用链表串起来，范围查询顺着链表读就行。哈希表不支持范围查询；二叉搜索树每个节点只有两个分叉，3000 万行要约 25 层；B 树的非叶子也存数据，扇出小，范围查询要在各层间来回跳。
2. 主键是 INT（4 字节），指针 6 字节，页大小 16KB，一行数据 1KB。三层 B+ 树大约能存多少行？ 非叶子一项 = 4 + 6 = 10 字节，一页能放 16384 ÷ 10 ≈ 1638 项，扇出约 1638。叶子一页放 16384 ÷ 1024 = 16 行。三层共 1638 × 1638 = 2 683 044 个叶子页，2 683 044 × 16 = 42 928 704 行，约 4300 万行。主键越短，扇出越大，同样三层能存的行越多。
3. orders 表主键 id，二级索引 idx_user_id(user_id)。下面哪条查询不需要回表？A. SELECT * FROM orders WHERE user_id = 7　B. SELECT id FROM orders WHERE user_id = 7　C. SELECT quantity FROM orders WHERE user_id = 7　D. SELECT created_at FROM orders WHERE user_id = 7 B。二级索引的叶子存的是 (user_id, 主键 id)，B 要的 id 索引里就有，是覆盖索引。A、C、D 要的列只在聚簇索引的叶子（整行）里，必须拿 id 回表。
4. 联合索引 (a, b, c)。下列哪个条件只能用上 a 这一列？A. a = 1 AND b = 2　B. b = 2 AND a = 1 AND c = 3　C. a = 1 AND c = 3　D. b = 2 AND c = 3 C。跳过了 b，在 a = 1 的那一段里 c 是乱的。A 用上 a、b；B 三列都用上（书写顺序不影响，优化器会调整）；D 缺了最左列 a，一列都用不上。
5. 联合索引 (user_id, status, created_at)，条件 user_id > 5 AND status = 'paid' 用上了几列？ 1 列（user_id）。user_id 是范围条件，能定位到 user_id 为 6、7、8、9…… 的一大段，但这一段里有好几种 user_id，status 只在同一个 user_id 内部有序，整体是乱的，所以从 user_id 之后停下。status = 'paid' 只能在这一段里逐项检查。可以在第 10 节的动画里点这个条件看。
6. user_id 上有索引。下列哪种写法会使索引失效？A. user_id = 8 - 1　B. user_id + 1 = 8　C. user_id IN (7, 8)　D. user_id BETWEEN 7 AND 8 B。索引按 user_id 本身排序，对列做了运算，就没法拿它在树里定位，只能每行算一遍 user_id + 1 再比，退化成全表扫描。A 的运算在常量一边，先算出 7 再查；C、D 是等值和范围条件，都能用索引。
7. EXPLAIN 的结果里 type 为 ALL、key 为 NULL，说明什么？Extra 出现 Using index 又说明什么？ type = ALL、key = NULL：没用任何索引，做的是全表扫描，通常要检查 WHERE 写法（是不是索引失效）或者考虑建索引。Extra = Using index：用了覆盖索引，结果只从索引里读，不用回表。
8. 为什么 InnoDB 推荐用自增整数作主键，而不推荐用 UUID？ ① 自增 id 一个比一个大，新行总是追加在聚簇索引的最后一页，几乎不会页分裂，页都是满的；UUID 是随机的，经常要插进已满的页中间，引发页分裂，挪数据、页半空。② 每个二级索引的叶子都存一份主键，8 字节的 BIGINT 比 36 字符的 UUID 小得多，二级索引也就小、扇出大。
