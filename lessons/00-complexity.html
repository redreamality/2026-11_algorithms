第 0 课 · 复杂度

复杂度说的不是“跑几秒”，而是数据变多时，要做的工作涨得多快。

先理解 核心对象 判断模板 应用场景 练习与自测

开始前要会：Python —— uv run 与 assert、f-string、推导式与生成器表达式、lambda、dict.fromkeys 与 Counter、类型标注、生成器只能走一遍；前面的课 —— 这是第一课，先读完预备课 · Python 基础即可。

先理解：工作量如何随数据增长

一个类比

你在班里找一个人：

  • 挨个问“你是小明吗？”：人数翻倍，问的次数也翻倍。这是 O(n)。
  • 让每两个人都握一次手：人数翻倍，握手次数变成 4 倍。这是 O(n²)。
  • 名单按字母排好了，每次翻到中间、扔掉一半：1000 人也只要翻 10 次左右。这是 O(log n)。

核心对象：复杂度档位

常见的几档（从快到慢）

写法n = 1000 时大约要做几步典型例子
O(1)1按下标取数组元素
O(log n)10二分查找（第 6 课）
O(n)1,000遍历一遍
O(n log n)10,000好的排序，比如 sorted()（第 8 课）
O(n²)1,000,000两层循环

表里的二分查找和排序后面会专门讲，这一课只需要记住它们各在哪一档。

动手：把 n 从 1 拖到 100，看 O(n²) 怎么把其他几档甩开（条形以 n² 为满格）。

判断模板：数循环与隐藏操作

怎么看出来

只看循环套了几层、每层跑多少次，常数和小项都扔掉：

for i in range(n):          # n 次
    for j in range(n):      #   × n 次
        ...                 # → O(n²)

for i in range(n): ...      # n
for j in range(n): ...      # + n  → 2n → 还是 O(n)

注意“藏起来的循环”：x in list、sorted()、list.insert(0, x) 看着只有一行，其实都不是 O(1)。

空间复杂度

同样的道理，问的是：额外开了多少内存？只用几个变量是 O(1)；新建一个和输入一样大的 set 就是 O(n)。 很多时候是拿空间换时间，这节课的练习就是例子。

应用场景：复杂度藏在一行代码里

日常 Python 代码里很少需要“专门写算法”，真正踩坑的往往是一行看着无害的代码。最常见的就是在循环里对 list 用 in：

场景用什么代价
反复问“x 在不在这批数据里”先转成 set 再查转一次 O(n)，之后每次平均 O(1)
查重len(set(items)) != len(items)O(n)
去重并保留顺序list(dict.fromkeys(items))O(n)
统计每个值出现几次collections.Counter(items)O(n)
拿不准哪种写法快标准库 timeit 量一下别猜
def new_customers(today_orders, known_customers):
    """今天下单的人里，哪些是新客户。"""
    known_set = set(known_customers)          # O(m)，只做一次
    return [customer for customer in today_orders
            if customer not in known_set]     # 每次 O(1)，整体 O(n + m)

# 如果直接写 customer not in known_customers（一个 list），
# 每次都要从头扫一遍，整体变成 O(n × m)：5000 个老客户、1000 个订单就是 500 万次比较。

完整可运行的版本在 examples/complexity_in_practice.py（uv run examples/complexity_in_practice.py），会用 timeit 打印两种写法的实际耗时。下面讲怎么一眼看出这种差别。

timeit 是标准库里的计时工具：timeit(函数, number=3) 把这个不带参数的函数连续调用 3 次，返回总共花了多少秒（一个 float）。要计时的代码带参数时，用 lambda 包一层：

from timeit import timeit

seconds = timeit(lambda: sorted(range(100_000)), number=3)
print(f"排序 3 次共 {seconds:.3f} 秒")

表里说 set 的 in “平均 O(1)”，为什么能这么快、为什么是“平均”，第 4 课讲哈希表时揭晓；现在先记住结论。

练习与自测

练习

场景：活动报名表里，有没有人用同一个邮箱报了两次？在 dsa/complexity.py 里用三种办法各写一遍，再写一个业务里真正会用的：

  1. has_duplicate_slow：两层循环，两两比较。O(n²)。
  2. has_duplicate_sorted：排好序后，重复的值一定挨在一起。O(n log n)。
  3. has_duplicate_fast：用 set 记住见过的值，碰到重复立刻返回。O(n)，但要 O(n) 的额外空间。它还要能接收生成器，比如 has_duplicate_fast(email.lower() for email in emails)，所以只能 for 走一遍。
  4. find_duplicates：把重复的邮箱都列出来，每个只列一次。O(n)。
uv run dsa/complexity.py                # 报名表的端到端例子，逐条打印期望和实际
uv run pytest tests/test_complexity.py

自测

1. 下面这段是 O(?)
i = 1
while i < n:
    i = i * 2
 O(log n)。i 每次翻倍，翻 log₂n 次就超过 n 了。
2. has_duplicate_sorted 为什么不能写 nums.sort()？ sort() 会改掉调用者传进来的列表，这是副作用。用 sorted(items) 生成一份新的。
3. 三种解法里，什么时候 slow 版反而合适？ n 很小（比如 10 个以内），或者内存极紧张、又不能改原数据的时候。复杂度只描述“n 很大时”的趋势。
